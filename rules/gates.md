# Gates

Judgment-based checkpoints that must never be silently skipped. Each stub is deliberately short — read it, then load the named skill for the actual procedure. A stub that looks complete invites acting on it alone; it isn't, the skill is.

- **Phase gate [CRITICAL]:** a feature file's frontmatter `phase` (`planning` | `implementation` | `review`) is the single source of truth for what work is permitted — it survives a session clear, the conversation does not. Check it on every restore *before doing anything else*. Planning forbids implementation code and branch creation; implementation forbids spec and checklist edits. Refuse out-of-phase work with the literal reply, and escalate a wrong spec rather than working around it. ⚠️ **The planning half is hook-enforced; the implementation half is not.** `hooks/phase-guard.sh` **is registered** (`settings.json:42-49`, `PreToolUse` on `Edit`/`Write`/`NotebookEdit`) and denies writes to source while an un-superseded `planning` feature file exists and no `implementation` file records the current branch — exempting `docs/*`, `.claude/*`, `settings.json`, `projects/*/memory/*`, `rules/*` and `skills/*` (the instruction surface: a rule or skill file is not implementation code, and two parked planning cards used to make every one of them unwritable repo-wide), plus the retired `CODING_MEMORY.md`/`coding-memory/*` — with no bypass variable. Nothing computational stops a spec or checklist edit mid-implementation — that half remains judgment-only, by design. Either way it is a momentum guardrail, not a security boundary. Procedure: `managing-session-memory`.
- **Gate transition [CRITICAL, hard stop]:** planning → implementation opens **only** on the literal user phrase `gate confirmed` — "continue", "yes", and "go ahead" are not permission. Until then: no branch, no first task. On confirmation, update the frontmatter, create and record the branch, start task one — and treat it as a mandatory `/clear` point. Procedure: `managing-session-memory`.
- **Model-switch checkpoints [CRITICAL]:** three, one per phase boundary — entering planning; planning → implementation (the unskippable one, covering all code/branch/PR/commit work including docs-only PRs and "small" housekeeping, mid-session even on a warmed-up frontier model); implementation → review. Each is its own ask; an earlier answer never satisfies a later one. Procedure: `managing-session-memory`.
- **Session freshness checkpoint [ENFORCED]:** after a major task, or roughly every ~35k tokens of new conversation, save memory and push before offering to clear the session — never the reverse order. Procedure: `managing-session-memory`.
- **Token-limit checkpoint:** near the token limit, ask whether to keep spending now or stop and resume after refresh. Procedure: `managing-session-memory`.
- **One-canonical-file discipline:** feature-scale work lives in a single `docs/features/<name>.md` (frontmatter + spec + checklist), updated in place — the default, and sufficient for nearly every feature. A synced `<name>.spec.md` half **MAY** be split off when the checklist file stops reading comfortably in one pass (frontmatter + task list stay in the `.md`; full spec, decisions, and Gherkin detail move to the `.spec.md`, read on demand only, never at session start) — this is a MAY, never a MUST, and most features should never split. Splitting still never licenses a separate "progress", "implementation summary", or "state of branch" document — two documents describing the same work means a reader cannot tell which one is wrong. Git is the record of implementation; ADRs under `docs/decisions/` remain required for structural, business-logic, and direction-pivoting decisions. Procedure: `managing-session-memory`.
- **Handoff/restore discipline:** a handoff is ≤~1,500 tokens — phase + `model_tier` header, current task, exact next step, blocking gotchas, pointers — and never restates spec or plan content. On restore, read the handoff, the active feature file, `git status`, and `git log main..HEAD`, then verify frontmatter against reality (a branch/phase mismatch is stop-and-report, not a guess). Nothing else loads until the current task demands it. Procedure: `managing-session-memory`.
- **Default-branch safety:** never commit application code directly to `main`/`master`. Enforced by `hooks/git-guard.sh` (Tier 1); the exception — documentation only: `docs/*.md` (by file type, so a script under `docs/` gets no free ride) — is encoded in the hook, and is now the whole allowlist: `CODING_MEMORY.md` and `coding-memory/*` were permitted here until that tree was retired. The guard also fails closed — refuses, no bypass variable — on a checkout it cannot name: a plain detached HEAD, a detached mid-rebase that will move `main`/`master`, and outside a git repository; it stands down only while git has an unrelated sequencer operation in progress (ADR 0026). Workflow: `preparing-pull-requests`.
- **Force-push safety:** a bare `git push --force`/`-f` is blocked on every branch by `hooks/git-guard.sh`; `--force-with-lease` is allowed on feature branches, blocked on `main`/`master`, a detached HEAD, and outside a git repository (ADR 0026).
- **Chained commands:** `git-guard.sh`, `doc-guard.sh` and `merge-guard.sh` all lex the command into shell segments (`hooks/lib/shell_segments.py`), so `git add -- x && git commit` is evaluated and a flag binds to the segment that owns it. `merge-guard.sh` joined them in ADR 0029, by moving onto the shared `gh` reader (`hooks/lib/classify-pr-command.py`) instead of its own inline classifier; that closed three silent bypasses at once — a chained `foo && gh pr merge`, a global option ahead of the subcommand (`gh -R o/r pr merge 5`), and a *stack* of wrappers (`time rtk gh pr merge 5`, where only a single literal `rtk` used to be stripped). A **redirection** is read as part of its command, not as a separator, so `git commit … 2>&1` no longer invents a pathspec and `> out git commit …` no longer hides the commit; the accepted cost is that *any* trailing bare digit before a redirect is dropped (a fail-open when that digit was the pathspec). Open shapes, the fail-closed/fail-open split, and rationale: ADR 0015 (amending 0013, amending 0012).
- **Dormant hooks:** `checkpoint-before-modify.sh` (demands a rollback point before a destructive command), `require-project-standards.sh`, `scan-invisible-unicode.sh` — three hook scripts that all exist and pass their tests but are **not registered in `settings.json` — they never run.** Wiring them up is open work; the invisible-unicode scanner in particular is advertised protection that is not currently protecting anything. `scan-secrets.sh` was in this list until it was registered under `PreToolUse`/`Edit|Write|NotebookEdit` — it had no test suite at the time (this bullet's earlier claim that it "passed its tests" was wrong; `hooks/scan-secrets.test.sh` was written alongside the registration).
- **Secret-command-guard [Tier 1]:** `hooks/secret-command-guard.sh` (`PreToolUse`/`Bash`) blocks a command that names a known secret-bearing dotfile/path (`~/.terminal_aliases`, `~/.bash_profile`, `~/.zshrc`, `~/.zprofile`, `~/.zshenv`, `.env`/`.env.*`, `credentials.json`, `*/Application Support/*/credentials*`), and blocks a full-environment dump (`os.environ`/`process.env` anywhere in the raw command text, or a bare `env`/`printenv` with no arguments). Written after this session leaked real secrets from `~/.terminal_aliases` twice via exactly those two shapes. **There is no permitted read shape** — v1 allowed a `grep`/`egrep`/`fgrep` call carrying an `-o`-family flag, on the theory that `-o` echoes only the matched substring; the caller picks the pattern, so `grep -o 'export .*'` reproduced the original leak verbatim and the classifier allowed it (measured 2026-08-28, and 23 green tests never asked). Carve-out removed whole rather than narrowed — ADR 0039. `.env.example`, `.env.template` and `.env.sample` are exempt from the `.env` family: they are conventionally committed and never carry a value, and without the exemption the guard blocked `git add .env.example`. **Fails OPEN** on missing python3, an unparseable payload, or any internal classifier error — the opposite direction from `scan-secrets.sh` above, because this hook's blast radius (nearly every Bash call, every session) is much larger than a single write. Bypass with `SECRET_EXEMPT=<reason> <command>` (logged); v1 shipped no hatch on the reasoning that the hook "only fires on narrow incident shapes, not ordinary work" — measurement refuted that, which is why the hatch exists.
  ⚠️ **Not a security boundary, and the deny message must not claim otherwise.** Five shapes are measured `ALLOW` and disclosed: variable indirection (`F=~/.zshrc; cat "$F"` — the lexer has the value and the classifier discards it), a path built by expansion, a read performed **inside a script file** (`bash diag.sh`), and the full-environment dumps that are not a bare `env`/`printenv` (`export -p`, `declare -p`, `set`, `env -0`, `printenv -0`, `ps eww` — widening was offered and declined, since bare `set` is common). **The script-file gap means the guard does not block leak #1's original form**, only its bare-`env`/`os.environ` cousins; do not read "both leaks are now blocked" into this bullet. Each gap is pinned by an `ALLOW` assertion in `hooks/secret-command-guard.test.sh`, so widening is a deliberate edit rather than silent drift. Design, the Known-gaps table and verification: `docs/features/secret-command-guard.md`; rationale: ADR 0039.
- **Remote-merge safety:** `gh pr merge` (a server-side PR merge from the CLI) is blocked by `hooks/merge-guard.sh` (Tier 1) — merges land through the GitHub UI with review, not autonomously mid-session; a local `git merge` and `gh pr create`/`view` pass. Still a momentum guardrail, not a security boundary — but as of ADR 0029 a chained `foo && gh pr merge`, a global option before the subcommand, and stacked wrappers are all caught (see **Chained commands** above); what remains open is the shared reader's own fail-open on exotic unparseable quoting. Bypass a genuinely intentional merge with `MERGE_EXEMPT=<reason> gh pr merge ...` (logged).
- **Documentation-checkpoint safety:** a `git commit` that makes a substantial source change but stages no documentation (`docs/` — which covers `docs/features/` and `docs/decisions/`) is blocked by `hooks/doc-guard.sh` (Tier 1) unless it carries a `Doc-Exempt: <reason>` trailer; trivial source-only commits pass. The same hook surfaces uncommitted work at the next session start (its PreCompact registration was ceded to the claude-code-handoff trio 2026-07-20 — ADR 0006 — which saves session state but does not check git status; a `/clear` itself cannot be blocked by any hook). *What* must be documented — business-logic changes and direction-pivoting implementations, each also earning an ADR under `docs/decisions/` — is defined in `managing-session-memory`.
- **Test-marker safety:** a `git commit` staging a file with a sibling test (`X.sh`↔`X.test.sh` / `X.py`↔`X.test.py`) at a version that test has never passed is blocked by `hooks/test-marker-guard.sh` (Tier 1) — the marker is a receipt that the suite ran against those exact bytes, never a grade (ADR 0027). Registered globally on `Bash` like its siblings, but **inert until a repo opts in** via `hooks/lib/write-test-marker.py`; the one exception is `MSG_NO_PYTHON`, which blocks everywhere. Bypass a genuinely exempt commit with `TEST_EXEMPT=<reason> git commit ...` — but that only rescues a real gate *decision*; **if the decision file itself is missing or broken, `TEST_EXEMPT` can't be read at all** (confirmed: still blocks), and recovery means fixing the file with Edit/Write instead of `git commit`. v1 ships no `--status`. Detail and the arming evidence trail: `docs/features/verification-marker-gate.md`.
- **Worktree-location safety:** work happens in a worktree, never the primary checkout, and a worktree lives at `~/.worktrees/<repo-name>/<worktree-name>`. Enforced in **two layers that fail in opposite directions**: layer 1 is `hooks/worktree-guard.sh` (Tier 1, `PreToolUse` on `Edit`/`Write`/`NotebookEdit` and on `Bash`) — it sees command *text*, refuses before git runs so the tree is untouched, and **fails open on any shape it cannot lex**; layer 2 is `hooks/reference-transaction`, a git hook armed separately via global `core.hooksPath` (`hooks/install-layer2.sh`, **not** `settings.json`), which sees the ref update rather than the command and **fails closed** on any `HEAD` write in the primary checkout — at the cost of leaving the destination's content staged in the shared tree, so a dirty tree after a refusal is the signal that layer 1 needs widening. `hooks/create-worktree.sh` handles `WorktreeCreate`/`WorktreeRemove`: it **redirects, never denies**, and refuses removal of a dirty worktree rather than `--force`ing it. Exemptions are written out, not inherited: `docs/*`, `.claude/*`, `settings.json`, `projects/*/memory/*`, `rules/*`, `skills/*`, `CODING_MEMORY.md`, `coding-memory/*`. **No repo opt-in** — unlike `phase-guard.sh`, every git repo on this machine is in scope, so a fresh clone denies guarded writes from its primary checkout until a worktree exists for it; that is the intended behavior. `WORKTREE_EXEMPT=<reason>` (logged) is **one escape hatch that clears both layers** — layer 2 honours it too (`reference-transaction:593`), so do not read the two arms as needing two different bypasses.
  ⚠️ **Currently `log` mode** — `settings.json` `env.WORKTREE_GUARD_MODE`. **Absent** means `log`; `deny` arms it; **any other value runs the guard in `deny` mode** and names the bad value in every refusal the mode governs (`worktree-guard.sh`, the `case "$WORKTREE_GUARD_MODE" in` block and both exits of `refuse()`; the two `hard_deny()` calls that fire before the mode is read cannot name it) — a mistyped switch is a failed attempt to arm, not permission to run unguarded. An exempt path stays writable under a mistyped value, so `settings.json` can always be fixed. ⚠️ That guarantee covers the mistyped-mode case only: three other refusals (`$HOME` unset, git below the version floor, the lib dir missing) fire before the exemption list is consulted while claiming otherwise — measured, open, tracked in the card's task-13 note. In `log` mode it records would-denies and blocks nothing. Flipping to `deny` is its own commit and needs three things: 7 days of use, **every arm having recorded at least one would-deny**, and every recorded line read and judged a correct refusal. Those criteria measure **precision, never coverage** — a refusal-only log reads *flawless* when the guard has gone blind to an entire shape.
  ⚠️ **While in `log` mode the guard is indistinguishable from not being installed.** The liveness report rides on a refusal that is actually printed (`worktree-guard.sh:236`), and `log` mode never prints one — so nothing running will tell you layer 2 is unarmed. Check it by hand (`git config --get core.hooksPath`) rather than assuming; it resolves itself when mode flips to `deny`.
  ⚠️ **What it does not cover, and the deny message must not claim otherwise.** The **Bash write surface** is not covered at all: the hook receives command text, never effects, so `npm install`, `make`, or a heredoc dirtying the tree is undecidable. Layer 2 backstops **`HEAD` moves and nothing else** — `git stash pop`, `git stash apply`, `git reset --hard HEAD`, `git revert`, `git merge --ff-only` and `git cherry-pick` all overwrite the shared tree with no `HEAD` transaction (measured), so for those six layer 1 is the sole defence and still fails open. **"The two-layer design fixed the fail-open" is false as a general claim.** A git call inside a script file or built inside an interpreter string is invisible to layer 1 by construction. `git bisect start` in a primary checkout now fails — deliberate; bisect in a worktree. The 4 pre-existing worktrees are **not** migrated, so two conventions live at once. **Not a security boundary** — four one-flag bypasses defeat layer 2, and `WORKTREE_EXEMPT` clears both layers (stated once, above); it raises the floor on accidents, which is the whole threat model. Design, boundaries and the measurement record: `docs/features/worktree-location-guard.md`; rationale: ADR 0038.
- **New-project setup gate:** in a new repo, or on first substantial work in a repo with no `.claude/project-standards.md`, run `setting-up-a-new-project` before writing project code. This absorbs the old "never scaffold in YOLO mode" rule — proposing structure/stack and waiting for confirmation is exactly what that skill's blocking-gate step does.
- **New-instruction gate:** before adding any new "always/never do X" rule, hook, or skill, run `triaging-new-instructions` to classify where it actually belongs.
- **Observability-judge gate:** after architecting a design and after implementing a change, run the observability judge before opening a PR — it scores the change against the evaluation and observability rubrics, relays a junior-dev summary, and records a verdict. Enforced by `hooks/judge-guard.sh` (Tier 1), which blocks `gh pr create` until a fresh implementation-stage verdict matches the current HEAD (strict); bypass a genuinely exempt PR with `JUDGE_EXEMPT=<reason>`. Procedure: `running-the-observability-judge`.
- **Subagent-commit verification gate:** after any implementer/fix subagent reports DONE with a commit SHA, before trusting that report, generating a review diff, or advancing to the next task — independently confirm the commit landed in the correct checkout. Not hook-enforced (no generic script can know which checkout is "correct" for a given dispatch); a subagent's own self-check instruction has repeatedly failed to catch this. Procedure: `verifying-subagent-commits`.
- **Durable-claim verification gate:** before writing any factual claim into a durable artifact — commit message, ADR, spec, PR body, memory file, handoff, code comment — run the command that settles it. Not hook-enforced, and deliberately so: ADR 0025 rejected keying a hook on claim-words because "works/fixed/done" fires on every Conventional-Commits `fix:` prefix. But the invariant at `rules/core-conduct.md` is advisory and has a long violation record, so the *procedure* now has a home rather than none. Procedure: `verifying-durable-claims`.
- **Spec-compliance gate:** after a spec/design doc is written and self-reviewed — and again after
  any later spec edit — run the compliance judge before the user review gate; a failing or missing
  verdict blocks `superpowers:writing-plans`. Persistent violations escalate to the user, never silently waived.
  Not hook-enforced (a `spec-guard` hook is deferred until this gate is observed being skipped).
  Procedure: `running-the-compliance-judge`.
- **Pane-dispatch redirect:** substantial agents run in terminal panes, not in-process — the two judges are hook-enforced (`hooks/pane-dispatch-guard.sh` denies their Agent dispatch when a terminal is available, outside the session policy; fails open, with a per-session cooldown after an adapter failure), read-only `Explore`/`Plan` stay in-process, and every other worker follows the per-session pane-split policy (`inline` / `panes max=N`, asked once at the first worker dispatch). Procedure: `dispatching-pane-agents`.
- **Context-handoff watch:** at its model-dependent threshold — 100k Sonnet, 130k Opus/Fable, 75k for anything unrecognised — `hooks/context-handoff-watch.sh` nudges the freshness checkpoint and prepares a press-Enter handoff pane, once per session — the automated arm of the session-freshness checkpoint above; the save-then-clear order still holds.
