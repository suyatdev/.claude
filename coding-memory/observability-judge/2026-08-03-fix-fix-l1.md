## What was changed

Round 1 judged the actual bug fix (two safety hooks that only checked the *first* command in a
chain, so `git add -- x && git commit` walked straight past them). That verdict said **low risk,
high confidence** and raised five points. This round judges only what the author did about them —
one commit, `af51f88`, six files, no change to the fixed hooks' core logic.

Four things happened:

1. **Both hooks' "I can't tell" behaviour is now pinned by tests.** `git-guard` and `doc-guard` do
   the *opposite* thing when their command-reader won't load: git-guard blocks everything
   (fail closed), doc-guard waves it through (fail open). That split was deliberate, but it lived
   only in a code comment — nothing would have complained if a future tidy-up made them match.
   Both directions are now tests.
2. **The `main` allowlist tightened from "anything under `docs/`" to "markdown under `docs/`."**
   Round 1's complaint was that the guard trusted a *folder* rather than a *file type*, so the day
   someone dropped `docs/deploy.sh` it would ride onto `main` unreviewed. Now it can't.
3. **ADR 0013 written.** Round 1 found `rules/gates.md` sending readers to ADR 0012 for the lexer's
   known limits, while the lexer had since moved to a different file. 0013 records the move and
   the fail-closed cliff, and amends 0012 rather than editing it.
4. **`rules/gates.md` trimmed.** Round 1 measured it +21% for a bug fix, in a file that loads on
   every single turn. Now +10%.

Think of it as the follow-up visit after the repair: the repair itself isn't touched, someone just
labelled the fuse box, put a tamper seal on the two switches that must stay in opposite positions,
and threw away the pile of old receipts stapled to the door.

## Does it do what you wanted?

**Yes — and these are real fixes, not the appearance of fixes.** You asked me to say that plainly,
so here is the evidence rather than the assurance.

I didn't just read the new tests; I broke the code three ways and checked the tests noticed.

| I sabotaged… | Expected the suite to… | It did |
|---|---|---|
| `git-guard` → made it fail **open** when the reader is missing | fail the 2 new fail-closed cases | **2 failed, 31 passed** — exactly those two, nothing else |
| `doc-guard` → made it fail **closed** on the same condition | fail the 1 new fail-open case | **1 failed, 15 passed** — exactly that one |
| `git-guard` → reverted `docs/*.md` back to `docs/*` | fail the 2 new file-type cases | **2 failed, 31 passed** — exactly those two |

That is what a test with teeth looks like: it fails when and only when the thing it names breaks.
A test that passes no matter what you do to the code is decoration, and none of these are.

The technique matters too. The "reader is missing" case is created by copying the hook to a folder
with no `lib/` next to it — which is genuinely how the hook fails, since it looks for its reader
beside itself. That's the real condition, not a stub pretending to be it. And doc-guard's fail-open
test is paired with a control that runs the *same* staged files through the *real* hook and
confirms they still get blocked — so a green there can't come from an empty fixture with nothing to
complain about. I flagged exactly that trap in round 1; it was closed properly.

On the other three:

- **`docs/*.md`.** I checked the claim independently: every one of the 35 files under `docs/` is
  markdown, and *no non-markdown file has ever existed under `docs/` anywhere in this repo's
  history*. I also checked the diagram skill, since "rendered diagrams" sounded like it might emit

  nothing today and nothing foreseeable.
- **ADR 0013.** Read in full. It's an honest record: it names the options that were rejected and

  pointer is the house style here, not an improvisation.
- **`gates.md` trim.** Measured, not taken on faith: 7,922 bytes on `main` → 9,552 after round 1
  → **8,725 now**. That's +10.1% over `main`, down from +20.6%. I also checked the deleted

## What could go wrong / what I'm unsure about

No dimension is a `fail`, and nothing here is a correctness defect. Four honest items:

**1. The "everything stops" cliff is documented now, but it is not gone.** `git-guard` runs on
*every* Bash command and refuses everything if `shell_segments.py` or `classify-git-command.py`
breaks. Round 1 raised it; this round pinned it with a test and wrote it into ADR 0013. Both are
genuine improvements — but a test stops the *direction* from silently flipping, it does not stop
the cliff from existing. The blast radius is the same size it was yesterday. It's the right
direction for a safety guard, the error message names the exact file, and you can still repair it
with the Edit tool because those aren't Bash-gated. Just don't read "now tested" as "now mitigated."

**2. `CODING_MEMORY.md` still says the allowlist was "widened to `docs/*`."** It wasn't touched in
`af51f88`. So the repo's always-loaded memory file now describes a policy the code no longer has —
which is the *exact same class of defect* as round 1's finding that `gates.md` pointed at the wrong
ADR, just one level down. One line, thirty seconds to fix, but it should be fixed before this lands
or the next reader inherits a false statement.

**3. The two hooks now treat `docs/` differently on purpose, and nothing says so.** `git-guard`
allows `docs/*.md`; `doc-guard` still counts anything under `docs/*` as documentation. That
asymmetry is *correct* — "is this documentation?" and "is this safe to land on `main` unreviewed?"
are different questions, and a screenshot is the first without being the second — but it is
undocumented and unpinned. That is precisely the shape of problem this round just fixed for the
fail directions: two hooks deliberately disagreeing, with nothing holding them apart.

**4. ADR 0012 still names the wrong file, for anyone who lands on it directly.** 0013 says "where
0012 says the lexer lives in `classify-pr-command.py`, read `shell_segments.py`" — which fixes the
reader coming *from* `gates.md`, since `gates.md` now points at 0013 first. A reader arriving at
0012 from a search or from `CODING_MEMORY.md` gets the stale name with no forward link. This
matches the repo's existing convention, so I'm not calling it a defect — just naming the residue.

Smaller: `gates.md` is still +10% over `main` for a bug fix. The two facts it added are
operationally load-bearing (which guards lex; which advertised protections never actually run), so
I think that's earned — but the dormant-hooks bullet should shrink to one line the moment those
hooks get registered. And, as in round 1, tests and implementation landed in the same commit, so
git history alone doesn't show red-then-green for the `docs/*.md` narrowing. I proved the red state
myself by mutation instead, so that evidence exists independently of the commit layout.

## What was changed

Two safety hooks in this repo were only half-awake, and this change wakes them up.

`git-guard.sh` stops you committing code straight to `main` and stops dangerous force-pushes.
`doc-guard.sh` nags you when you commit a big code change with no documentation. Both decided
"is this a `git commit`?" by checking whether the command *started with* the words `git commit`.

That works for `git commit -m msg`. It does **not** work for
`git add -- file && git commit -m msg` — which is the shape this repo types all day long. The
guard looked at the first word, saw `git add`, shrugged, and said "not my problem," then exited
reporting success without having checked anything at all.

Think of a bouncer who only checks the ID of the first person in a group and waves the rest
through. Everyone learned to walk in second.

The fix stops reading the command as one long string and instead chops it into the separate
commands the shell will actually run (`a && b ; c`), then asks the question about each one. The
chopping logic was **not newly invented** — `judge-guard.sh` already had a working, tested version
of it, so the shared half was lifted out into `hooks/lib/shell_segments.py` and both now use it.
One lexer, one set of known limits, instead of three regexes drifting apart.

Along the way, three more bugs fell out of writing the tests, all caused by searching the whole
command string for flags instead of the flag's own command:

| Command | Before | After |
|---|---|---|
| `git push --force && echo --force-with-lease` | **allowed** — a "lease" anywhere excused a bare force anywhere | blocked |
| `git push && echo --force` | **blocked** — a false alarm | allowed |
| `git commit -m msg && ls -a` | doc-guard judged every dirty file, not the commit | judges the commit only |

The `main` allowlist was also widened to include `docs/*`, and one false claim in `rules/gates.md`
(that `phase-guard.sh` enforces the phase gate — it isn't even registered) was corrected.

from the merge-base and ran both versions side by side in a throwaway git repo:

| `git push --force && echo --force-with-lease` on a feature branch | **exit 0 (fail-open)** | exit 2 |
| `git push && echo --force` | **exit 2 (false alarm)** | exit 0 |

## What could go wrong / what I'm unsure about

Nothing here is a correctness defect in the shipped path. Three things I'd still name out loud:

**1. A new "everything stops" failure mode (the one that matters).** `git-guard.sh` now fails
*closed* — if it can't inspect a command, it blocks it. That's the right direction for a safety
guard. But `git-guard` runs on **every Bash command**, so if `classify-git-command.py` or
`shell_segments.py` goes missing or breaks, *every* Bash command is blocked. I tested it: with a
deliberately broken `shell_segments.py`, plain `ls -la` returns exit 2. Before this change, only a
missing `python3` could do that; now one shared file is a single point of failure across three
live hooks. Mitigations are real — the file is committed and tested, the error message names the
exact file, and you can still repair it with the Edit/Write tools since those aren't Bash-gated.
But it's a cliff that didn't exist yesterday, and it is the one new behaviour the new test suites
do **not** cover (I verified it by hand instead).

**2. The `docs/*` allowlist is a genuine policy loosening.** Anything under `docs/` can now be
committed straight to `main` with no review. Today that's safe — I checked: 34 files, all
markdown, nothing executable. The reasoning (without it the fixed guard would start blocking the
daily docs workflow and read as a regression) is sound and was user-ruled. But the guard now
trusts a *directory* rather than a file type, so the day someone drops a script under `docs/`,
it rides to `main` unchallenged.

**3. Documentation debt in the audit trail.** No ADR was written, and two decisions here look
ADR-worthy by this repo's own rule ("ADRs required for structural, business-logic, and
direction-pivoting decisions"): widening a stated safety gate's allowlist, and turning a lexer
into a shared dependency of three live hooks. Concretely stale as a result: `rules/gates.md` now
points readers to **ADR 0012** for the accepted lexing limits, but ADR 0012 still says *"the
classifier now lives in `hooks/lib/classify-pr-command.py`"* and documents the lexer rationale
there — the code moved to `shell_segments.py` and the ADR wasn't amended or marked superseded.

Smaller notes: `rules/gates.md` is always-on context and grew **7,922 → 9,552 bytes (+21%)** for a
bug fix, much of it historical narration that's also recorded in `CODING_MEMORY.md`. And tests
and implementation landed in the same commit (`ac5afa2`), so git history alone doesn't show
red-then-green — though I reproduced the red myself against the merge-base, so that evidence
exists independently of the commit layout.

## What I'd double-check before merging

1. **Decide whether the total-Bash-lockout cliff is acceptable**, and if so pin it with a test —
   a case asserting `git-guard` exits 2 with a useful message when the classifier is unavailable,
   and that `doc-guard` still exits 0 on the same condition. Right now the two hooks' opposite
   fail directions are documented in comments but not enforced by anything.
2. **Amend ADR 0012** (or add a short new ADR) so it points at `shell_segments.py`. `gates.md`
   sends readers there for the accepted limits and it currently names the wrong file.
3. **Confirm the `docs/*` widening is what you want long-term** — consider whether it should be
   `docs/**/*.md` rather than any file under `docs/`.
4. **Trim the `gates.md` additions.** The historical "until 2026-08-03 both anchored..." narration
   and the dormant-hook bullet are already in `CODING_MEMORY.md`; always-on context is the
   expensive place to keep them.
5. Sanity-check the five dormant hooks finding is genuinely filed as follow-up work —
   `scan-secrets.sh` and `scan-invisible-unicode.sh` are advertised protection that never runs.
   Correctly out of scope here, but it shouldn't evaporate.
