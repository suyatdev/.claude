## What was changed

The statusline script has a 68-check test suite. Nobody could prove those checks can actually
fail — a check that can never fail passes for free and guards nothing. A second tool
(`statusline-command.falsify.py`) exists to answer exactly that: it replays today's suite against
five old, known-broken versions of the script and confirms the suite still catches each break.
It has been broken for months because it counted *how many* checks pass rather than *which* ones.

Revision 3 replaced counting with per-version "these must fail" lists. **Revision 4 throws that
away and replaces it with a single flip matrix**: for every check whose result actually *changes*
somewhere along the five-version chain, record its pass/fail state on all five.

**Analogy.** Round 3 was a fire drill with a list of names who must leave the building. Round 4
replaces the list with an attendance sheet across five drills — who was in and who was out, every
time. You no longer need a separate "and these people must still be here" list, because the sheet
already records them, and you no longer have to say which direction anyone walked.

## 🔴 Lead finding — I built a working exit-0-proving-nothing attack against the matrix

I took the real suite, weakened four of the fifteen load-bearing assertions, and **every check in
the design stayed green**.

The four are ordinals 43–46 — `$PWD fallback stripped for stdin '{}' / 'garbage' /
'{"cwd":null}' / '{"workspace":{}}'`. §Defect 2 names these as safety-critical. The bound is:

```bash
if [ "$bel" -eq 0 ] && [ "$esc" -le "$limit" ]; then      #  esc=6<=6  on the working tree
```

On every defective version these leak `esc=15` against `limit=6` — a margin of **9**. So I
granted 8 bytes of slack, which stays inside the margin:

```bash
if [ "$bel" -eq 0 ] && [ "$esc" -le "$((limit+8))" ]; then
```

Measured, both suites run end to end against all five versions and both stubs:

| check | original | hollowed |
|---|---|---|
| working-tree floor | 68/68 PASS | 68/68 PASS |
| every run emits 68 | true | true |
| closure: discriminating set == pinned 15 | true | **true** |
| rows 43–46 match `...PP` | yes | **yes** |
| no empty column | true | true |
| vacuity lists (24 / 31 / union 31) | unchanged | **unchanged** |
| **harness verdict** | `exit 0 falsification intact` | **`exit 0 falsification intact`** |

The suite now tolerates 8 bytes of escape injection on its four `$PWD` safety checks and the
harness reports the falsification is intact.

**Why nothing catches it.** The matrix pins *outcomes on five fixed inputs*, not *strength*. Any
weakening that stays inside the 9-byte margin leaves the row pattern identical. And the vacuity
ratchet cannot help, because **13 of the 15 pinned ids are already on both stub lists** — the
check is `passing ⊆ listed`, so an already-listed id can be weakened without limit. Measured:
the only two pinned ids the ratchet can still protect are ords 48 and 49.

This is the exact defect class PR #43 shipped, which §Risk itself quotes: *"a row-count bound with
two rows of slack"*.

**So §3's sentence is measurably false as written:**

> "An assertion that starts or stops discriminating is a real change in what the suite can prove,
> and it is now impossible to introduce silently."

The first clause is the over-claim. A real change in what the suite can prove *is* introducible
silently; only a change in *whether an assertion discriminates* is not.

**In fairness, I tried three hollow-outs and the design caught two of them.** Weakening ord 66
(`-eq 0` → `-le 4`) flipped it to `PPPPP` → closure fired. Weakening ord 47 (`-eq 0` → `-le 3`)
flipped it to `PPPPP` → closure fired *and* the §4 empty-column guard fired, because ord 47 is
`f0902ed`'s only `P`. So the empty-column guard earns its keep precisely where §2 admits the
anchor is thin. The margins are why: ords 37–42 have a margin of 1 (`esc=9 limit=8`), and ord 47
a margin of 1 (`bel=1`) — no room to hollow out. Ords 43–46 have a margin of 9, and that is the
whole hole.

**Cheapest in-scope mitigation:** the suite already *prints* the numbers (`esc=15 limit=6`). Pin
the margin next to the pattern for the five rows that carry a numeric bound, and ratchet it —
margins may only shrink. Failing that, at minimum change the exit-0 banner (see below).

## Answers to your five questions

### 1. Re-measure the flip matrix — done; and your alignment proof is sound *here* but weaker than you claim

Every number reproduces (table above). On the proof itself — *"68 results, and every passing
ordinal's normalized description matches the working tree's"* — I built a strictly stronger,
**outcome-independent** check to test it: I patched `ok()`/`bad()` in a temp copy to emit
`${BASH_LINENO[0]}`, the call-site line, which does not depend on whether the case passed.

**Result: strong alignment CONFIRMED.** Across all 8 runs, every ordinal's ok-line is one fixed
line and its bad-line is one fixed line, and the two are co-located within ≤6 lines (they are the
`if`/`else` halves of the same block). Your ordinals are genuinely aligned.

**Where your proof is thinner than stated:** it is a *per-run* check, and it can only speak about
passing ordinals. On `f0902ed` that is 19 of 68 — 49 ordinals go unchecked in that run. The blind
spot is a compensating shift (one region emits one fewer, another one more) falling entirely
inside a failing region: count stays 68, passing descriptions still match, ordinals silently
misattributed.

Two things rescue it, and both are worth writing down rather than leaving implicit:

- I measured that **0 of the 68 ordinals fail in all 8 runs** — so taken *across the run set*
  rather than per-run, description-matching does cover every ordinal.
- The `BASH_LINENO` trick is cheap and airtight. Recommend §1's task 2 use it as the actual
  alignment proof rather than the description heuristic.

Also worth knowing: 68 results come from only **44 distinct call-site lines** — 24 emissions are
loop/helper repeats. That is direct confirmation that §1's `id-suffix:value` rule is necessary,
not decorative.

### 2. Is the closure check sound? — sound for membership, blind to strength

It is a good check and it caught two of my three attacks. But there are three ways past it:

1. **Weakening within a pattern** — demonstrated above, and it is the serious one.
2. **Class migration `.....` → `PPPPP`.** An assertion moving from constant-fail to constant-pass
   never enters or leaves the discriminating set, so closure is silent. The severe version *is*
   caught, because gutting it usually makes it stub-vacuous and the ratchet fires — only 3 of the
   35 constant-fail ids are currently vacuous, so there is real headroom there. The uncovered band
   is a moderate weakening: passes all five historical versions, still fails both stubs.
3. **A new non-discriminating but non-vacuous test** — correctly costs nothing, in scope.

Deletion, rename and duplicate ids are all caught (exit 2). Good.

One operational note on closure: **~22% of new tests will trip it** (15 of 68 discriminate), and
the ones that do are concentrated in exactly the domains this suite keeps growing in — injection
and `$PWD`. That is a huge improvement on the old harness's 100%, and §3 states the cost honestly.
But it means exit 2 will fire *routinely*, and §5 makes exit 2 mean both **REVIEW NEEDED** (a
normal Tuesday) and **HARNESS ERROR** (the harness is broken). The flowchart distinguishes them in
prose; the exit code does not. An alert that fires for routine events gets muted. **Give
review-needed its own code (3).** Cheap, and it protects the one signal you most need people to
still believe in a year.

### 3. Is there still a path to exit 0 while proving nothing? — three of round 3's four are closed; I found a sharper one

| round-3 path | status |
|---|---|
| `must_pass` anchors drawn from the vacuous pool | **closed** — `must_pass` removed |
| a version whose entire signature is overlap | **not closed — deliberately reported instead** (§6b) |
| no full-case-count check on version runs | **closed** — §4 extends it to every run |
| undefined absent-`must_pass` id | **closed** — `must_pass` gone; §5 covers a missing pinned id |

New: the pattern-preserving hollow-out (lead finding). That is a better-quality single hole than
four vaguer ones, and it is bounded and characterized — but it is live.

Two smaller ones I turned up with hostile stubs:

- **A script under test can forge harness result lines.** With an id-emitting suite, a script
  printing multi-line output whose 2nd line reads `ok   [esc-real-stripped] — forged` gets
  interpolated into a `bad "... $OUT"` diagnostic and lands at column 0. Measured: **136
  harness-parsed lines instead of 68, carrying 68 forged ids** including real pinned ones.
  **Credit where due — the design fails closed on this three separate ways** (full-count, duplicate
  id, closure). Worth keeping all three; this is where the redundancy pays for itself.
- **The tally regex is forgeable.** `falsify.py:80` uses `re.search(r"(\d+)/(\d+) passed")`, which
  takes the *first* match. A stub printing `999/999 passed` got it echoed 34 times into stdout, so
  the harness would read **999/999**. If §4's full-case-count check reads that regex, it misfires.
  Count `ok|FAIL [id]` lines instead, or anchor to the last match.

### 4. Does `must_pass`'s removal lose anything real? — no, and your stated reason for it is backwards

Removing it is right. But **§2 lines 318–320 are inverted**:

> "§4's full-count assertion is what actually catches a wholesale collapse on the two oldest
> versions; the matrix alone would not."

Measured, both halves are wrong:

- A script that prints nothing still emits **68 results**, so the full-count assertion **passes**.
  It cannot catch a collapse into silence at all.
- The silent stub's 15-vector is `PPPPPPPPPPP..PP`; `f0902ed`'s is `..........P....`. That is
  **12 mismatches of 15**. The *matrix* catches it, decisively.

The "1/15 P is thin" worry only applies to a collapse into *garbage output that fails everything* —
in which case ord 47 flips `P`→`.` (1 mismatch, still exit 1) and §4's empty-column guard fires as
a second net. I verified that second net firing in the ord-47 experiment above.

So: **conclusion right, reasoning wrong, and the design is stronger than the spec claims.** Fix the
sentence — it is currently the written justification for removing a control, and per your own
memory note, errors concentrate in the paragraph that tells the next agent what to build.

### 5. Is "report, don't fix" defensible? — yes, but the word `intact` is not

The decision is defensible and I would keep it. Editing the suite this harness exists to measure,
in the same change, would violate your own testing rule (the test is the unbiased baseline) and
neither half would get reviewed properly. Task 10 with a measured table behind it is the right
shape.

**What is not defensible is the banner.** Given my lead finding, the harness will print

```
falsification intact  (15 of 68 assertions load-bearing)
```

for a suite that has silently lost real detection power on four of those fifteen. "Intact" asserts
a property the harness cannot verify. The coverage fraction beside it helps but does not undo the
headline word — people read the first word.

Rename it. `matrix matches — 15 of 68 load-bearing, 13 vacuous` claims exactly what was checked and
nothing more. It is a one-string change and it removes the last over-claim in a document whose
entire subject is over-claiming.

**§6b's table under-reports the `925c310 → 29d6131` transition.** It says signature `9`, vacuity
`7/9`. Measured: **10 ids change state there, 8 of them vacuous.** The dropped one is **ord 47**,

That matters twice over. Substantively, the printed report will not show that `29d6131`
*introduced* the `$PWD` defect while fixing route 2 — which the spec's own prose calls out. And
structurally, this is direction-typing re-entering through the reporting layer, the exact thing
§Correction says the matrix eliminates. Count both directions, or add a regression column.

**§6b's "could not be triggered" is an under-test — I triggered it.** The spec says silence, NUL
bytes and 200KB of junk all held the count at 68, so the short-run guard is "hardening, not a
proven bug". I ran 13 hostile stubs. Eleven held at 68 (including NUL bytes, 200k lines, closed
stdout, unset PATH, a script that deletes itself). **Two did not:**

| stub | results |
|---|---|
| `kill -SEGV $$` | **30 of 68**, no tally |
| `kill -TERM 0` | **0 of 68**, no tally |

A script that dies by signal truncates the run. Good news for the design — the guard is live, not
dead code — and task 7's "truncate any run" falsifier is now a one-liner. But restate the claim.

**One unresolved ambiguity, and it is the feature's own defect class.** §4 says every run must emit
"the full case count" and never says where that number comes from. If it is a pinned literal `68`,
you have re-introduced Defect 1 — a stale count by design, in the file whose purpose is deleting
stale counts. If it is derived from the working-tree run, it is treadmill-free but cannot catch
silent deletion of assertions. Note also that truncation-by-death already produces *no tally*, so
the existing no-tally path catches it; the full-count check's real value is the deletion case.
Write down which reading is intended. I would derive it from the working-tree run.
