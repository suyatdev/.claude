## LEAD FINDING — `success_masking` is a **fail**

**The stated test plan goes green while `git commit -am x` walks straight through the gate.**
Measured just now on git 2.50.1 in a throwaway repo, not recalled:

```
foo.sh edited in the worktree, never staged
git diff --cached --name-only --diff-filter=d HEAD  ->  []      (zero paths)
git commit -am x                                    ->  ships foo.sh = v2
```

The form table (§"Which paths, and which content") defines `ALL` as `-a`/`--all`. It says nothing
about bundled short options. A classifier that token-matches `-a` and `--all` classifies `-am` as
**`PLAIN`**, takes the index collector, gets **zero paths**, finds no pairs, and **allows** — while
the commit ships content no suite ever ran against. That is byte-for-byte the round-1 `-a` fail-open
the spec's own bullet claims to have closed, resurrected through flag bundling.

Two things make this a `fail` rather than a `concern`:

1. `hooks/doc-guard.sh:132` already carries the comment "`commit -a`/`--all`/`-am` stages tracked
   edits at commit time" — a sibling guard in this repo has **already** learned that `-am` is a
   distinct lexical case. This spec re-loses that knowledge.
2. Checklist task 2 says the classifier suite covers "every `form`". Forms are enumerated **by name**
   (`PLAIN`/`PATHSPEC`/`ALL`/`INCLUDE`/`INVALID`/`FOREIGN`), not by spelling. A suite that asserts
   one representative spelling per form passes 100% green with this hole open. The mutation floor
   does not catch it either: the `ALL` allow/door mutants are exercised through `-a`, which works.

A second instance of the same class, also measured:

```
foo.sh: index = v3, worktree = v4;  bar.md staged
git commit -m y foo.sh          ->  commits foo.sh ONLY, at HEAD:foo.sh = v4  (the worktree blob)
```

A pathspec **without** the `--` separator is legal git and behaves exactly like `PATHSPEC`. If the
classifier recognises operands only after `--` (the repo's house style, and the only spelling the
spec ever writes), this classifies `PLAIN` → index collector → hashes **v3** → matches a marker
written for v3 → **allows a commit that ships v4**. That is the round-1 "PATHSPEC content" fail-open,
verbatim, for the no-`--` spelling. Note also `bar.md` was staged and **not** committed, so the
`PLAIN` path set would have been wrong in the false-block direction too.

**Root cause, singular:** the wire contract specifies the `paths` **field** ("the pathspec operands")
but never the **grammar** that produces it — how operands are recognised, and how bundled short
flags and option-arguments (`-m`, `-F`, `-C`, `--author`) are consumed. Everything else in this
document is measured to the exit code. This one paragraph is not, and it is the paragraph the whole
control rests on.

The fix is bounded and additive — specify the lexing grammar, add two scenarios, add two classifier
test bullets. The architecture does not change. That is why risk stays `medium` and not `high`.

## Does it do what you wanted?

Mostly, and the reasoning quality is high. The four questions you asked, answered directly:

**1. Does it leave a silent fail-open?** Yes — two, both measured, both above. Neither lives in the
three areas you nominated; they live one layer under all of them, in the unspecified lexing grammar.
Your three nominated areas came out better than you feared but not clean:

- *Out-of-path-set content rule.* The three rows are correct. I checked `ALL` against the nastiest
  case — a file staged at v2 with worktree v1 — and `git commit -a` resets the index to the worktree,
  so "worktree blob" is right. But **pair formation is defined only from the test side** ("a test file
  whose derived subject is not tracked forms no pair"). The path set contains *subjects* far more
  often. A tracked subject whose sibling test exists in the worktree but is **untracked** has no
  defined rule: check worktree existence → pair forms → ABSENT → block; check tracked-ness → no pair
  → **allow, no marker demanded**. The spec does not choose, and the two choices land on opposite
  sides of fail-open.
- *ABSENT vs `MSG_GIT_FAILED`.* `git cat-file -e <base>:<path>` exits **128** for a missing path —
  the same code a corrupt object store or an unresolvable `<base>` produces. Exit code alone cannot
  separate them, so genuine infrastructure failure is reported as `MSG_STALE_TEST` ("re-run the
  suite"), which will not help. Fail-**closed**, so not a fail-open, but the door taxonomy is wrong
  and the remedy string misdirects.
- *The bash pre-filter.* Two problems. (a) The flowchart puts "Runnable command?" (node C, which
  reads the classifier's `kind` field) **before** the pre-filter (node D), while §Latency says the
  pre-filter "runs before any `python3`". Both cannot be true. (b) If the pre-filter genuinely runs
  first, a Bash payload whose command is empty or whitespace contains neither `git` nor `commit` →
  exit 0 → **`MSG_NOTHING_RUNNABLE` (door 2) becomes unreachable**, contradicting the doors table and
  the fail-closed contract. And the spec never says *how* bash gets the command out of the JSON
  payload — `hooks/judge-guard.sh:42` does `payload=$(cat)` and delegates **all** parsing to python,
  so there is no established bash-side accessor to inherit.

**2. Is the fail-closed contract honestly scoped?** Nearly. "Every git invocation is status-checked,
apart from the two whose non-zero exit is a defined answer" is **off by one**: the tracked-ness probe
used for pair formation (`git ls-files --error-unmatch`) is a third status-unchecked-by-design call,
and its failure direction is **allow** (no pair → no marker demanded). Everything else in that
section is scoped accurately, including the accepted-open list, which is unusually honest.

**3. Is global-but-inert observable?** No, and this is the design's weakest observability property.
The spec argues well for a greppable file as the opt-in signal, and task 12 mandates documenting the
scope in two places — but at the moment of a commit **nothing distinguishes "allowed because
verified" from "allowed because inert."** Both are a silent exit 0. `hooks/judge-guard.sh:204`
records this exact failure in this exact hook family: "a gate that looks armed and does nothing."
Task 14's first-arming check is a one-time manual probe, not an ongoing signal. An engineer landing
in an unfamiliar repo has no in-band way to answer "is this on?"

**4. Are the doors and the floor sound?** The arithmetic is right this time — 14 distinct constants,
no duplicates, stale-subject and stale-test correctly split. Coverage is not: doors **3–6**
(`MSG_NO_PYTHON`, `MSG_CLASSIFIER_MISSING/FAILED/BAD_OUTPUT`) appear **nowhere in the flowchart**;
node E has two exits and a classifier failure reads as "not COMMIT → **ALLOW**." That is the *same
prose/diagram contradiction class* as the `FOREIGN`/`TEST_EXEMPT` defect this round just fixed, in
the same artifact — and the diagram is what an implementer follows. Door 2 is unreachable (above).
The allow-path list says "the seven" but the flowchart has **nine** allow edges: the pre-filter allow
and the happy-path match are unlisted, so the honest floor is 24, not 22. (22 is a floor, so it is
not *wrong* — but the accounting is presented as exhaustive and is not.)

**5. Is the test strategy sound?** Substantially yes — production path (payload on stdin, throwaway
repo, real commits not simulated), the inventory assertion correctly relocated to task 8, the wiring
commit behaviour-neutral and separate. But the revert-pair warning **names the wrong pair**. The
writer lands at **task 5**; task 7 is the gate. Reverting task 7 alone does *not* leave "14 suites
calling a deleted writer" — the writer is still there and the wiring keeps working harmlessly. The
pairing that actually breaks 14 suites is **5 ↔ 8** (writer deleted, 14 suites hit `|| exit 1`).
The second clause ("reverting the wiring alone blocks every commit") is correct for 7 ↔ 8. Two
distinct hazards were collapsed onto one pair and the first was mis-stated.

## What could go wrong / what I'm unsure about

- Both fail-opens ship if implemented as written. Nothing in the document warns an implementer, and
  the specified test plan is green either way.
- **Unborn HEAD is undefined.** Measured: in a repo with no commits, `git diff --cached --name-only
  --diff-filter=d HEAD` exits **128**. Under "any non-zero exit → `MSG_GIT_FAILED` → block", the
  first commit of any writer-installed repo is blocked with an infrastructure message. The empty-tree
  fallback (`4b825dc…`) is defined **only** for `--amend` on a root commit.
- **§Architecture names the wrong lexers.** It says `git-guard.sh`, `doc-guard.sh` and
  `merge-guard.sh` lex `git commit`. Measured: `merge-guard.sh` lexes `gh pr merge` and contains no
  `git commit` regex, while **`hooks/checkpoint-before-modify.sh:97`** — unnamed — does. The total
  "four call sites" is coincidentally right (3 real + 1 new); the *named set* is wrong in both
  directions, so the "unify the four lexers" follow-up would edit a file with nothing to unify and
  miss one that matters.
- **Markers are gitignored only by this repo's root-anchored `/hooks/state/`.** The spec says the
  cover "does not travel" but does not make the writer establish one. An adopting repo will **track**
  its marker store, and then a receipt written by someone else certifies content for you — the store
  is the sole authority for letting a commit through. Low likelihood, but it is a trust hole created
  by the global-but-inert decision.
- The design's own revert point, commit `6046565`, sits on **`main`** staging
  `docs/features/verification-marker-gate.md`. `hooks/git-guard.sh:89-106` allows commits on `main`
  only when every staged path matches `CODING_MEMORY.md|coding-memory/*`, and git-guard **is**
  registered on Bash PreToolUse (`settings.json:17`). I cannot tell from here whether it was made
  outside the guarded path, chained past the anchored `^git[[:space:]]+commit` regex, or the guard
  fail-opened. I am not asserting which. I flag it because it is live evidence for this document's
  own thesis — the coverage this hook family claims outruns what it delivers.
- Credit where due: the new classifier's `FOREIGN` rule flags a `cd` **anywhere** before the commit,
  which is strictly stronger than git-guard's anchored regex. The chained-command blind spot that
  exists elsewhere in this family is genuinely closed here.
