# Observability verdict — falsify harness: defect signatures instead of pass counts

- **Stage:** architecting (advisory — does not gate a PR)
- **Repo / branch:** `statusline-followups` / `main`
- **HEAD:** `aa464ff127155feaf217f5fde84b4c159802fa11`
- **Spec judged:** `docs/features/falsify-harness-signatures.md` (`phase: planning`, `branch: none`)
- **Timestamp:** 2026-08-08T05:07:00Z
- **Risk:** medium · **Confidence:** high

---

## What was changed

A spec, not code. It proposes rewriting the "test-of-tests" (`statusline-command.falsify.py`), whose
job is to prove the statusline test suite is capable of failing at all. Today that harness checks an
exact *pass count* for each of five old buggy versions of the script. Counts are facts about how many
tests exist, so the harness breaks every time somebody adds a test — it has been red and ignored for
a while. The spec swaps counts for **named lists of assertions that must fail** on each old version,
lets anything else fail freely, and treats a signature naming a test that no longer exists as a hard
error.

Think of it as a smoke detector you test by lighting a match. Today it's wired to "exactly nine
alarms must sound" — add a tenth detector and it reports a fault. The spec rewires it to "*these*
three detectors must sound." Sensible. The problem is what it stops checking.

## Does it do what was intended?

Half yes, half over-claimed.

**It genuinely ends the false alarms.** That part is correct and well-argued, and the underlying
insight — a count measures the suite, not the defect — is exactly right.

**It does not restore as much falsification power as the document implies.** I ran the harness and
measured. Of 68 assertions in the suite, this design will put roughly **11** under falsification
coverage — the injection/stripping family. The other 57 get none, under the old scheme or the new
one. The spec's opening line ("68 tests and no proof any of them can fail") stays true for 57 of them
after the fix, and the document never says so.

## What could go wrong

**Lead finding — `success_masking: fail`. The harness can print "falsification intact" while one of
its five versions proves nothing.**

`4d63b09` is labelled "cosmetic only" and scored 20/20 under the old counts — it fails *nothing* in
the safety family. Under the new scheme its `must_fail` list is therefore **empty**, and an empty list
is satisfied by any input at all: the right blob, the wrong blob, a truncated file, a stub. Nothing in
the design flags a version that contributes zero assertions. One of five versions becomes decoration.

Related, and worse: I ran the suite against a script that does nothing (`#!/bin/bash; exit 1`) and
**23 of 68 assertions passed**, including *every* injection assertion, all four `$PWD fallback
stripped` cases, and `a control character in a path never reaches the output`. They are "count of bad
byte ≤ limit" checks, and silence satisfies them. That is the vacuous-assertion class this harness
exists to find, sitting in the safety-critical tests, and neither the old nor the new design measures
it.

**Second finding — the case-identity contract does not exist.** §1 says cases are identified by "the
description string the suite already prints." The suite prints a **different string on pass than on
fail**:

```
ok   — all-control cwd falls through to a stripped $PWD (bel=0)
FAIL — all-control cwd leaked via the $PWD fallthrough (bel=3)
```

Measured on `29d6131`: **27 of 40** failing cases have a fail-name that cannot be derived from any
working-tree pass-name — and that unmatchable set contains the actual defect signatures for `29d6131`
and `e882659` (`$PWD fallback leaked control bytes…`, `all-control cwd leaked…`). The spec's one
worked example comes from `assert_no_injection`, the single family where the desc *is* a stable
prefix. It generalises from its best-behaved case.

The consequence: §3's three-state check is **not implementable** as written against the output
contract §Non-goals freezes. Naming the fail-side string makes it work, but then "present-and-passing"
becomes unobservable — a suite that stops detecting a defect reports `ERROR: missing case` instead of
`the suite no longer detects this defect`. The alarm still fires; the diagnosis is wrong. §3 and
§Non-goals contradict each other, and the contradiction is load-bearing.

**Third — "extra failures allowed" gives up more than the spec admits.** The spec concedes it loses
"fails more than expected" and calls that the right trade. Measured, the loss is larger: about **31 of
the ~40–50 failures per version are era noise** — these 2024-era scripts predate the context bar,
sigma, locks, quota, worktrees and wrapping entirely, so they fail those tests for reasons having
nothing to do with their defect. The count gave a crude upper bound that at least detected "this
version is failing wholesale." The signature scheme has no such anchor. A small named `must_pass` list
per version would restore it at **zero** treadmill cost — a named list, like `must_fail`, does not grow
when the suite grows. The spec correctly diagnosed *counts* as the problem and then discarded the
entire "something still passes" direction with them.

**Fourth — §5's residual risk is named, not mitigated.** The harness runs at PR time by human memory.
Human memory is the mechanism that already failed. Documenting that honestly is good practice and
still leaves the failure mode fully armed.

## The unread signal (spec §"Measured evidence") — resolved

The spec flags that `f0902ed` and `925c310` each lost exactly one pass as the suite grew, "which
growth alone cannot cause." I chased it.

- Against the era-appropriate suites (`ae34fc7`, `5f4295b`, 20 cases), the recorded counts match
  `EXPECTED` **exactly**: 9, 10, 15, 20, 19. The counts were correct when written. The harness was
  broken *by growth*, not born broken — the spec's diagnosis is right.
- The flip is real but **benign, and three cases, not one**: `baseline renders model and token
  segments`, `sub-1000 tokens render raw, not k-formatted`, `tokens >=1000 render in k form` all moved
  pass → fail on both versions. These are token-bar baseline assertions tightened when the context bar
  landed. No label is wrong; no test is broken.
- The spec's "lost exactly one pass" is a **net** figure that concealed 3 losses against 2 gains.

The spec's *handling* is where I'd push back: tasks 2–4 schedule the investigation alongside the
rewrite, but §4's compare step is **blind to this class by construction** — a case that flips pass→fail
on an old version was never in `must_fail`, so the prediction/result comparison cannot see it. The
migration deletes the counts, which are the only artifact that ever recorded the anomaly. Resolve it
*before* task 4, not during.

## Procedural hazard, flagged deliberately

§4's whole value is pre-registration: predict signatures *before* running. A verdict file that
enumerates each version's observed failures would destroy that discipline for whoever implements this.
**I have deliberately not listed the per-version failing sets here.** The findings above are structural
and can be acted on without reading the answers off the output. The three flipped cases named in the
section above are non-injection rendering tests, never signature candidates, so naming them is safe.

## Concerns

1. `4d63b09`'s `must_fail` list is empty by construction; an empty signature is satisfied by any input, so one of five versions can never fail the harness and nothing flags it.
2. MEASURED: 23/68 assertions pass against `#!/bin/bash; exit 1` — including all 6 `assert_no_injection` cases, all 4 `$PWD fallback stripped` cases and `a control character in a path never reaches the output`. The vacuous-assertion class sits in the safety tests and the design never measures it.
3. MEASURED: 27/40 failing cases on `29d6131` have a fail-name underivable from any pass-name; the suite prints different text on pass and fail. §3's three-state check is unimplementable against the contract §Non-goals freezes. The spec's one example is drawn from the only family where it works.
4. §3 and §Non-goals contradict each other; the contradiction is load-bearing and will surface at task 4.
5. MEASURED: ~31 of ~40–50 failures per version are era noise (scripts predate the bar, sigma, locks, quota, worktrees, wrapping). "Extra failures allowed" leaves no anchor proving a version failed for its own defect. A named `must_pass` list would restore it at zero treadmill cost.
6. Coverage is over-claimed: ~11 of 68 assertions gain falsification coverage; the spec's framing implies the whole suite.
7. §4's compare step is blind to a pass→fail flip on an old version by construction, and the migration deletes the counts that recorded it. Resolve the anomaly before task 4, not during.
8. RESOLVED BY ME: era-appropriate suites reproduce `EXPECTED` exactly (9/10/15/20/19), so the counts were right when written. The flip is 3 token-bar baseline cases, benign; "exactly one pass" was a net figure masking 3 losses against 2 gains.
9. §5's PR-time-by-human-memory risk is documented but unmitigated — that is the mechanism that already failed once.
10. VERIFIED BY ME: the `rtk` git-proxy hazard is live today — a quoted `git show <sha>:statusline-command.test.sh` from the Bash tool mangled the argument mid-review. Keeping extraction in Python with the `#!` check is correct and still necessary.

## What I would fix before implementing

1. Add a per-version `must_pass` anchor list (named, so it never grows with the suite), and make an empty `must_fail` list a hard error.
2. Decide and document which string a signature names, and either give the suite a stable outcome-independent case id or drop the §Non-goals freeze. §3 cannot survive as written.
3. Add a vacuous-pass check: run the suite against a no-op script and assert that every case in every signature *fails*. That is a cheap, direct measurement of the exact class this harness exists to catch, and it currently would flag 23 cases.
4. State the real coverage — roughly 11 of 68 — in the harness output, so "falsification intact" cannot be read as more than it means.
5. Resolve the §"Measured evidence" anomaly before task 4 (it is already resolved above; record it).
