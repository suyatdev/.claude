**Round 1's failure mode was narration — a figure labelled "re-measured" that no instrument covered.
It did not recur.** Every claim in round 2's table is true. The only imprecision I found is
cosmetic: the spec says a failed collector "exits 128" where `git diff` outside a repo actually
exits **129**. The stated *rule* — "a non-zero exit from **any** collection or hashing command" — is
correct, so nothing load-bearing rests on the number.

I also caught and retracted a wrong finding of my own mid-review: an over-strict regex made it look
like only 2 of 11 suites declared the `$fail` tally the call-site snippet depends on. Re-measured
properly, **all 10 shell suites declare `fail=0` and end with `[ "$fail" -eq 0 ]`.** The snippet fits.

### The protocol swap is a net gain, not a quiet drop

You asked whether replacing the two-line `OK` protocol with one JSON line preserved the four
`judge-guard` fail-open defences. **All four survive, and two are stronger:**

| defence | round 1 | round 2 |
|---|---|---|
| existence ≠ usability | `kind` validated | **7 fields** domain-validated → `MSG_CLASSIFIER_BAD_OUTPUT` — stronger |
| answers-then-dies | leading `OK` sentinel | a leading sentinel only proves the process *started*; a JSON object must **parse**, which proves it *finished* — a mid-write kill yields truncated JSON → block. Plus `v == 1` and `MSG_CLASSIFIER_FAILED` on non-zero/empty — **stronger** |
| parse failure vs. empty | one sentinel | three distinct doors: `MSG_BAD_PAYLOAD` / `MSG_CLASSIFIER_FAILED` / `MSG_NOTHING_RUNNABLE` — stronger |

| `python3 -I` | present | "at every call site" — preserved |

Nit only: the contract says "exactly one line" but the validation says "parses as a JSON object". The
spec should say the hook reads **all** of stdout and rejects extra lines, not just parses line 1.

## What is still wrong

### 1. `FOREIGN` contradicts itself, on a door that fires in every repo on this machine

The flowchart routes `E{Foreign} -- yes --> V[BLOCK]` **without passing through** the `TEST_EXEMPT`
node `F`. The prose (spec:270–272) says the message tells you "to set `TEST_EXEMPT`". One of the two is
wrong, and an implementer must guess — on a blocking door whose reach I measured as machine-wide:

- `~/.claude/settings.json` is the **global** user config; matcher `Bash` fires in **every repo**.
- Node `E` precedes path collection (`G`/`H`) and the pairs check (`J`) entirely. So a `cd`-prefixed
  commit blocks **even when the commit contains no sibling-tested file at all, in any repo.**
- The trigger is "a `cd`, a `git -C`, `--git-dir`, or `--work-tree` anywhere before the commit" — so
  `cd "$HOME/.claude" && git commit` blocks too, a **same-repo false block**.

The justifying premise is also incomplete: "resolving `--show-toplevel` from its own cwd" is not the
only option. The PreToolUse payload carries a `cwd` field and this repo's own
`hooks/context-handoff-watch.sh:45–46` already consumes it (`jq -er '.cwd // empty'`, falling back to
`$PWD`). And `git -C <literal path>` **names its target explicitly** — knowable, not ambiguous.

Proportionality: this is round-1 concern #7's failure mode returning at larger scale — *a control that
mandates a routine bypass teaches the bypass* — except that per the flowchart the bypass doesn't even
work. `git-guard.sh` and `doc-guard.sh` face the identical ambiguity on the identical command and both
**allow**; `phase-guard.sh` solved the "which repo" problem properly (resolve from the write target,
line 192: *"Resolved from the WRITE TARGET, never from the session's cwd"*) and gated itself with a
`docs/features` opt-in. This spec adopts neither precedent and mentions no scoping at all
(`opt-in`/`opt in`/`global`: **0 occurrences**).

### 2. No latency budget, on a chain I measured at ~373 ms

The classifier is what *decides* whether a command is a commit, so it runs `python3` on **every Bash
tool call**, not just commits. Measured on this machine (10 runs each, payload on stdin):

```
git-guard   58.6 ms      bare `python3 -I -c 'import json'`   56.3 ms
doc-guard   81.7 ms      ──────────────────────────────────────────
judge-guard 165.8 ms     current PreToolUse/Bash chain    ≈ 373 ms
merge-guard 66.6 ms      a 5th python-spawning guard adds ≥ 56 ms
```

`phase-guard.sh` sets the house precedent for exactly this — it measured `11ms -> 38ms per write` and
argued the trade-off explicitly. This spec measures four tool versions but not its own cost
(`latency`/`performance`: **0 occurrences**).

### 3. The spec never surveys the hook chain it is joining

`git-guard` / `doc-guard` / `merge-guard`: **0 mentions each.** Two of them already lex `git commit`
with `commit_re='^git[[:space:]]+commit([[:space:]]|$)'` — `^`-anchored, so they silently skip
`git add -A && git commit -m x`. A fourth, operator-aware Python lexer will disagree with them on the
same command. That divergence is pre-existing, not this spec's fault, but joining a 4-hook chain
without reading it is how the next inconsistency gets built.

### 4. Task 8's completion criterion covers 11 suites; the spec supplies a snippet for 10

- **No Python call-site form.** Pair #6 (`hooks/lib/classify-pr-command.py` ↔ `.test.py`) is in the
  table and in task 8, but the only snippet given is shell, keyed on `$fail`. That suite ends
  `sys.exit(main())` — no `$fail`, no shell. Round-1 concern #9 flagged "a shell snippet offered to a
  Python suite"; the path resolution was fixed, this half was not.
- **`hooks/judge-guard.test.sh:13` does a persistent top-level `cd "$TMP"`** into a directory it then
  `git init`s. There, `$(git rev-parse --show-toplevel)` resolves to the **throwaway repo**, so the
  snippet points at a `write-test-marker.py` that does not exist and turns that suite red. The spec
  names the hazard generically ("a suite that `cd`s during its run captures both at the top instead")
  but never measures *which* suite triggers it. I measured it: exactly 1 of 11 — every other suite's
  `cd`s are subshell-scoped (`( cd … )`) and do not persist.

### 5. The `INVALID` allow-path sits outside the mutation floor

`INVALID` is safe as specified — measured, git exits 128 and commits nothing, so the hook allowing is
correct. But it is the one **allow** path that `form` introduces, and the mutation strategy is "one
mutant per door", where every door is a *block* message. A mutant that widens `INVALID` — e.g.
classifies any pathspec commit as `INVALID` — turns the gate off for **this repo's dominant commit
shape** while all eleven door-mutants still pass. The strongest control in the plan has a blind spot
aimed at the exact form round 1 failed on.

### 6. The frozen-inventory test is a real instrument, but an unscheduled one

You asked whether it genuinely converts a silent drop-out into a red test. Mostly yes — it is a real
assertion over `git ls-files`, and it is the right generalisation of round 1's lesson (the author
correctly refused to just fix `10`→`11`). Credit where due.

But it only fires **when someone runs `write-test-marker.test.py`**. Consider a rename that orphans a
subject: `panes/foo.sh` → `panes/foo2.sh` with the suite left behind. The commit's path set contains
`foo2.sh`, which has no sibling test → no pair → **allow**. The commit touches neither
`write-test-marker.py` nor its suite, so nothing forces the run. The spec's claim — "a rename that
silently drops a subject out of the gate turns that test red" — is true only conditional on someone
running it. The instrument exists; the trigger does not. (The converse is a genuine strength: *adding*
a pair is self-enforcing, because committing the new subject demands a marker, which demands the
wiring.)

### 7. `PATHSPEC` + `--amend` is the one table cell that does not hold the stated principle

Measured. Amended commit has `keep.sh` = `k1`; index = `k2`; worktree = `k3`. Then
`git commit --amend --no-edit -- foo.sh`:

```
COMMITTED keep.sh = k1      (the amended commit's version — index k2 and worktree k3 both ignored)
COMMITTED foo.sh  = v2      (worktree, as the PATHSPEC row says)
actual commit contents vs parent:  foo.sh  keep.sh
spec PATHSPEC formula (base=HEAD^, paths=foo.sh) returns:  foo.sh        ← keep.sh missing
```

The design's principle is that `base=HEAD^` re-verifies the amended commit's whole contents; that
holds for `PLAIN` and `ALL` but the pathspec dominates and narrows it away. Low consequence — the
carried content is what was already committed — but "All three forms combine with `--amend` unchanged;
`--amend` alters only the base" is stated as measured fact in a table presented as exhaustive, and for
this cell it is imprecise.

### 8. `paths` is unvalidated while `exempt` is carefully validated

`exempt` gets a length cap and a control-character regex, re-validated hook-side. `paths` gets "a list
of strings" and nothing else, then flows into `git diff --name-only <base> -- <paths>` in a bash hook.
The spec says nothing about argv-vs-shell-string (`argv`/`quoting`/`injection`: **0 occurrences**).
Core-conduct requires validating input at system boundaries; the asymmetry between the two fields is
the tell. Severity is low — the command's author is the agent itself — but it is one sentence to close.
