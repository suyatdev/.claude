## What was changed

Nothing has been built yet — this is a plan for reorganising how this repo remembers things
between sessions.

Today there are two notebooks. One (`CODING_MEMORY.md`) has grown to 2,491 lines / 231 KB —
about 58,000 tokens, against a documented cap of 200 lines. The other (`.claude/session-state.md`)
is small, accurate, and rewritten every prompt — and *nothing reads it*. So the useful notebook is
ignored and the dangerous one is the only place to look.

The plan:

1. **Auto-read the small notebook at session start** via a new quiet hook
   (`hooks/handoff/slim-session-start.sh`). It never blocks, never errors out loud, and if the file
   is bigger than 8,192 bytes it prints a path instead of the contents.
2. **Retire the big notebook as something you read.** It becomes a write-only archive — you only
   ever append to it, and you find things in it through search, never by reading it whole.
   Append-only is a *correctness* requirement, not tidiness: other documents in this repo cite it
   by line number (verified — `git-guard-empty-index.md`, `stale-phase-guard-rule-text.md`), so
   any trim silently breaks those citations.
3. **Split each feature document into a pair** — a short checklist file and a long spec file — with
   a new blocking hook (`hooks/feature-sync-guard.sh`) that refuses to commit if the two files'
   task lists disagree.
4. **Defer the search-index repair to a Phase 2** on a separate branch, because the index is
   currently 18 days stale and — verified directly against `memory-index/memory.db` — indexes
   **0** of 228 sources from `docs/features/`.

## Does it do what you wanted?

Mostly yes, and the reasoning behind it is strong.

The best thing about this spec is that it **doesn't sell you anything**. It states plainly that
session-start cost goes *up* (~4,634 → ~5,934 tokens) and that "any claim of token savings would
be unsupported." I re-measured the always-on files myself — 18,789 bytes across `CLAUDE.md`,
`rules/*`, and `MEMORY.md` — and the ~4,634 figure checks out. That is exactly the honesty standard
this repo asks for, and it is rare.

It also finds the *real* root cause: a rule file (`preparing-pull-requests`:12) told the system to
keep appending forever with no counterpart trim. "It behaved as specified; the specification was
wrong" is the correct diagnosis, not a guess.

Where it falls short of "yes" is that the **benefit is not stated in a form anyone can later check.**
Think of it as insurance. You know the premium exactly: +1,300 tokens, every single session, forever.
You know the payout size: 58,000 tokens avoided. But nobody has written down **how often the claim
gets made** — how many past sessions actually read that file whole. If it happens less than roughly
once every 45 sessions, this plan costs more than it saves, and nothing in Phase 1 would ever tell
you. The spec says the 58k case is "removed by construction", but the construction is a *documentation
rewrite* (task 3) plus a scenario saying reading it is "a defect, not a judgment call". No hook stops
a read. That's removed by instruction — and this spec's own root cause is an instruction that was
faithfully followed and wrong.

## What could go wrong / what I'm unsure about

**1. Both new hooks are quiet, and quiet hooks in this repo have already failed silently.**
`slim-session-start.sh` is modelled on `memsearch-nudge.sh`. Look at what that model is doing right
now: it printed "2332 chunks of past-session memory indexed" at the top of this very session — a
confident, healthy-looking line — while the index behind it was last built 2026-07-18 and contains
zero of the documents this plan depends on. The pattern's known live failure mode is *reporting
success over stale data*. The new hook copies it and adds no age marker: `.claude/session-state.md`
is emitted under `=== Handoff ===` with no indication of when it was written. This repo already has
three files (`context.md`, `task-history.md`, `recent-prompts.md`) that rotted since 2026-07-24
without anyone noticing. A stale handoff presented as current is worse than no handoff.

**2. The size cap degrades in the wrong direction, silently.** I read `hooks/handoff/live-handoff.sh`:
the trimming is not mechanical — it *asks the model* to trim when the file exceeds 80–120 lines. So
the "~1.3k, self-trimming" size rule in the design table is a soft convention, not a guarantee. The
file grows precisely when the work gets complicated. And at >8,192 bytes the new hook drops the body
for a one-line pointer — so on the messiest sessions, when you most need the handoff, you silently
get the least. That's a sensible fallback, but the failure is invisible from inside the session.

**3. The dormant-hook precedent is not addressed, and here it is load-bearing.** Four of the twelve
scripts in `hooks/` pass their tests and are **not registered** in `settings.json` — I confirmed this
directly: `checkpoint-before-modify.sh`, `require-project-standards.sh`, `scan-invisible-unicode.sh`,
`scan-secrets.sh` appear nowhere in the registration list. The repo has *already written down* this
exact hazard: `hooks/judge-guard.test.sh:344` says settings.json is "a different file with no test
covering it, and that hidden dependency is exactly what produced the wrong behaviour." Tasks 2 and 4
do say "register at ..." — good — but **no task adds an assertion that the registration exists.**
That matters most for `feature-sync-guard.sh`, because decision 6 knowingly departs from the
one-canonical-file gate *specifically* on the strength of that hook making divergence unstageable. A
hook that quietly never fires converts a declared, mitigated trade-off into an unmitigated one, and
the only symptom is that nothing ever gets blocked — which looks identical to everything being fine.

**4. `FEATURE_SYNC_EXEMPT` leaves a trail that evaporates.** The contract says `# logged`. In this
repo "logged" means `printf ... >&2` — I checked `judge-guard.sh:230` and `merge-guard.sh:93`, and
there is no `~/.claude/logs` directory at all. So a bypass of the guard that is the sole mitigation
for the rule departure above is recorded only in a transcript that gets cleared. For a Tier-1 gate,
that is not an audit trail.

**5. Phase 2's acceptance criterion is a smoke test wearing a quality gate's badge.** "A query naming
the active feature returns ≥2 hits from that feature's own documents" is measurable and has a real
baseline (0 today) — that part is good. But: a feature document *contains its own feature name*, so
once `docs/features/**` is indexed at all, ≥2 lexical hits are close to automatic. It therefore
mostly proves "indexing ran", not "retrieval is useful". It also fixes no `k`, sets no relevance-score
floor (today's hits score ~0.02 — the criterion would pass at that quality), says nothing about
precision of the *other* results, and asserts nothing about the new refresh trigger actually firing.
And "a query" is singular, chosen after seeing the index — the same shape as a fixture that
pre-creates the state it is meant to test.

**6. Two smaller things.** The spec says task 5 migrates "the other 6 feature files"; there are
**7** in the tree (`ls docs/features/*.md` minus this one) — an off-by-one in the task explicitly
flagged as "the expensive one", whose scope (all of them vs. only the two in `implementation`) is
still undecided *inside* the branch. And splitting feature files into a pair changes the shape that
`phase-guard.sh` — a Tier-1 hook — reads to find frontmatter; the spec never states what happens if
the `.spec.md` half also carries a `phase:` key.

## What I'd double-check before merging

- **Write the falsifier for the benefit before writing the code.** One line in the spec: "Phase 1
  succeeds if X". Cheapest honest version: grep past sessions for how often `CODING_MEMORY.md` was
  actually read whole, and re-measure session-start tokens after. If the frequency turns out to be
  near zero, that is a legitimate reason to keep the archive change and drop the +1.3k loader.
- **Put the handoff's age in the emitted header** (`=== Handoff (written 2026-08-06 01:15) ===`).
  One line of code; it is the whole difference between "here is the state" and "here is state that
  might be two weeks old", which is the exact failure already sitting in this repo.
- **Add a registration assertion to both hook test files** — a grep of `settings.json` for the hook
  path. Four dormant hooks and a test file that already names the hazard is enough precedent.
- **Decide what "logged" means for `FEATURE_SYNC_EXEMPT`** before implementing it — either a durable
  append-only sink, or say plainly in the contract that it is stderr-only and the bypass is not
  auditable after the session.
- **Settle task 5's scope (2 files or 7) and state a rollback plan** before starting it, and take a
  checkpoint commit first — `checkpoint-before-modify.sh` exists but is dormant, so nothing will
  demand one for you.
- **Tighten Phase 2's gate** when you get there: fix `k`, add a score floor, use a query set rather
  than one query, and pick the queries before looking at the rebuilt index.
- **Confirm `phase-guard.sh`'s behaviour against the pair shape** — which half owns `phase:`, and
  what happens if both do.

## Concerns

1. Benefit is unfalsifiable as stated: certain +1.3k/session against an unmeasured *frequency* of the 58k tail case; break-even ≈ 1 occurrence per 45 sessions, never computed
2. "58k worst case removed by construction" overstates it — removed by instruction (task 3 doc rewrite); no hook prevents reading `CODING_MEMORY.md`
3. `slim-session-start.sh` emits the handoff with no age/mtime marker; three sibling files already rotted undetected since 2026-07-24
4. Silent-on-failure design gives no signal distinguishing a working hook from one that stopped firing; `memsearch-nudge.sh` is the live precedent, reporting 2332 chunks over an 18-day-stale index
5. `session-state.md` trimming is model-prompted (`live-handoff.sh`, 80–120 lines), not mechanical, so the >8,192 B pointer path degrades inversely to need, silently
6. No registration assertion planned for either hook despite 4 dormant hooks in `settings.json` and `judge-guard.test.sh:344` already naming this exact hazard
7. Decision 6's departure from the one-canonical-file gate rests entirely on `feature-sync-guard.sh` firing; a dormant Tier-1 hook silently voids the mitigation and looks identical to compliance
8. `FEATURE_SYNC_EXEMPT` "# logged" means stderr-only per house convention (`judge-guard.sh:230`, `merge-guard.sh:93`); no `~/.claude/logs` exists, so bypasses are unauditable after the transcript clears
9. Phase 2 acceptance (≥2 hits from the feature's own docs) is near-automatic once `docs/features/**` is indexed — measures "indexing ran", not retrieval quality; no `k`, no score floor (today ~0.02 would pass), single hand-picked query chosen after seeing the index
10. Phase 1 has no acceptance criterion; no post-change token measurement is planned
11. Task 5 miscounts scope — spec says 6 other feature files, tree has 7 — and the 2-vs-7 migration decision is left open inside the branch
12. Pair shape changes what `phase-guard.sh` reads; frontmatter ownership between `<name>.md` and `<name>.spec.md` unspecified, and a duplicated `phase:` key could deadlock writes
13. No rollback plan for the pair migration; `checkpoint-before-modify.sh` is dormant so no checkpoint will be demanded
14. Always-on budget grows on both sides — +1.3k at session start and new text in `rules/gates.md`, already 9,459 B of an 18,789 B always-on total
