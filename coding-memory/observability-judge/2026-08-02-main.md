## Lead finding — `git commit -- <path>` commits the WORKTREE, and the design compares the INDEX

This repo's own standing convention is that **the `-- <path>` restriction must be on every
`git commit`** (global memory, `feedback_git_commit_pathspec_scoping.md`; reaffirmed in
`CODING_MEMORY.md` at `1859c30` as "the standing `-- <path>` rule"). So the dominant commit shape in
the repo the gate protects is the pathspec form.

The content-resolution table (spec:139–144) has exactly two rows: `-a`/`--all` → worktree, and
**"otherwise" → the index entry from `git ls-files --stage`**. A pathspec commit falls into
"otherwise". It should not:

```sh
git init -q .; printf 'v1\n' > foo.sh; git add foo.sh; git commit -qm init
printf 'v2-INDEX\n'    > foo.sh; git add foo.sh   # index    = v2
printf 'v3-WORKTREE\n' > foo.sh                   # worktree = v3, unstaged
git commit -qm pathspec -- foo.sh
git show HEAD:foo.sh
#=> v3-WORKTREE          (the design would have hashed v2-INDEX)
```

`git commit <paths>` commits the named files' **current worktree content, disregarding the index**.
So: run the suite green at v2, stage v2 (marker matches), edit to v3, `git commit -- foo.sh`. The
gate hashes the index (v2), the marker says v2, **it allows** — and git ships v3, a version no test
has ever seen. That is a silent fail-open, in the primary path, produced by the repo's house style.

It is precisely the bug the `-a` row exists to prevent ("reading the index here would compare stale
content and wrongly allow", spec:204). The spec found one member of that family and stopped. It is
also *not* covered by the accepted-open list, which names only lexing gaps (backticks, `eval`,
`sudo` wrappers, path-qualified `git`) — a `git commit -- hooks/foo.sh` lexes perfectly.

The same shape breaks the other direction too: a pathspec **narrows** the commit set, so an
index-based collector over-collects and blocks on files that are not being committed.

```sh
printf 'v3\n' > foo.sh; git add foo.sh; printf 'bar2\n' > bar.md
git commit -qm narrow -- bar.md
git show --stat --name-only --format= HEAD
#=> bar.md only          (an index-based collector would also have demanded a marker for foo.sh)
```

**This is cheap to fix now and expensive to fix later** — which is the entire reason for judging at
the architecting stage. It needs one more table row (`pathspec present` → worktree content, set
narrowed to the pathspec) and one more Gherkin scenario.

## Answers to the four questions put to this round

### 1. Does the design leave a silent fail-open anywhere? — **Yes. Two, plus one unlit surface.**

The four `judge-guard` fixes are genuinely *reused*, not merely name-dropped. Each is restated with
its **mechanism**, and the mechanism is the right one:

| claimed fix | mechanism in the spec | verdict |
|---|---|---|
| existence ≠ usability | `kind` output-validated to `COMMIT`/`NO`; marker validated on `version`, blob regex, both paths | genuinely closed |
| classifier answers then dies | sentinel protocol: `OK` on line 1, checked as `case "$parse_rc:$parse_ok" in 0:OK)` — status **and** shape | genuinely closed |
| parse failure indistinguishable from empty | sentinel again; `MSG_NOTHING_RUNNABLE` for the empty case | closed **for the payload** |
| `tool_name`-keyed skip returning early | "the command decides; `tool_name` only settles what an ABSENT command means" | genuinely closed |

So the answer to the narrow question — did it copy the fixes or just cite them — is: **it copied
them.** That part of the spec is strong.

But the fixes were applied only to the surface that already had them. The hook introduces an
entirely **new** subsystem — interrogating git — and none of that discipline is extended to it:

**(a) The `-a` scenario is unreachable from the described mechanism.** The table branches the *hash
source* under `-a`. It never branches the *path set*. But the spec's own scenario has the subject
"edited but **never staged**" (spec:201), and an index-based collector sees nothing at all:

```sh
printf 'v2\n' > foo.sh          # modified, never staged
git diff --cached --name-only   #=> (empty)
git diff --name-only            #=> foo.sh
```

Empty set → "Any pairs? no" → **ALLOW** (flowchart node H). The spec's headline
`MSG_STALE_SUBJECT` scenario silently passes unless collection unions in unstaged tracked
modifications under `-a`, which the spec never says.

**(b) A failed git call is indistinguishable from a legitimate "no pairs".** Node F "Collect
committed paths" has no status check specified anywhere, and the "These block" enumeration
(spec:248–250) lists python3, payload, classifier, marker, nothing-runnable — and **no git failure
at all**. If `git ls-files` errors, if `rev-parse --show-toplevel` fails, if `hash-object` fails,
the natural coding of the flowchart yields an empty set → ALLOW. This is fail-open class #3 from
`judge-guard` ("a parse failure indistinguishable from a legitimate empty case") reappearing
verbatim in a new component. The spec inoculated the old surface and left the new one bare.

**(c) Unlit: which repo?** The store is correctly resolved from `git rev-parse --show-toplevel`
"never `$HOME`" — the right lesson from `fix/judge-guard-verdict-lookup`. But the spec never says
**from which directory** that `rev-parse` runs. A PreToolUse hook sees `cd /other/repo && git commit
-m x` as one Bash command; if the hook resolves the root from its own cwd it reads the wrong repo's
index and the wrong repo's markers. Allow or block, both are wrong, and neither is named.

### 2. Is the fail-closed contract honestly scoped? — **Honest in form. Incomplete in content.**

Nothing in the contract is an *overclaim*. It abandoned the "any inability to verify blocks"
formulation that RUN 4/RUN 5 killed on `judge-guard`, and replaced it with two positive
enumerations. That is the correct shape, and the "This is a momentum guardrail, not a security
boundary" line (spec:66) is properly load-bearing rather than decorative.

The defect is the opposite of overclaiming: the **blocking list omits the failure surface the hook
newly introduces**. Six conditions are listed; git-subsystem failure — the one subsystem this hook
adds that `judge-guard` never had — appears in neither list. A reader cannot tell whether it blocks
or allows, and per finding (b) the honest answer is "allows".

One narrower imprecision: `MSG_NO_MARKER` is specified to name `"bash hooks/foo.test.sh"` as the
remedy (spec:187). For `hooks/lib/classify-pr-command.py` that instruction is wrong, and for the two
orphan suites (below) it names a suite that cannot produce a marker at all.

### 3. Are the observable signals adequate? — **The principle is right; the enumeration is missing.**

"`exit 2` is not one door… every block reason gets its own named constant… the suite asserts the
message, not just the code" is exactly the correct response to the 48-indistinguishable-assertions
finding. But the spec then names **five** constants —

```
MSG_BAD_MARKER  MSG_NO_MARKER  MSG_NOTHING_RUNNABLE  MSG_STALE_SUBJECT  MSG_STALE_TEST
```

— while its own blocking list and flowchart imply **at least eight** doors (unusable `python3`;
unreadable payload; missing classifier; empty classifier; wrong-output classifier; plus the five).
The unnamed three are the ones a mutation test is least likely to reach. A spec that states the rule
without the table lets an implementation satisfy the letter while collapsing exactly the doors that
were collapsed last time.

The mutation check (task 9) is scoped to a **two-mutant minimum**: reroute one door, empty the
classifier. Against ~8 doors, passing that says almost nothing about the other seven. The control
that caught the last mutant is being re-run at a fraction of its former strength.

Two further signal gaps: the **marker key normalisation is undefined** (the writer takes `$0`; the
store key is "the repo-relative subject path" — a suite run as `cd panes && bash adapters.test.sh`
yields `$0=adapters.test.sh`, and without `git ls-files --full-name`-style normalisation the marker
lands under a key the gate will never look up, producing `MSG_NO_MARKER` immediately after a green
run). And the `TEST_EXEMPT` log has **no persistent destination** — `judge-guard` writes its
exemption to stderr only, which vanishes. That precedent is tolerable for a rare human PR
exemption; this gate's exemptions will be routine (see below), and exemption drift is the exact
erosion path the control exists to prevent. Nobody will ever be able to count them.

### 4. Is the checklist's test strategy sound? — **The strategy is right. The inventory it rests on is wrong.**

The strategy itself is the strongest part of the spec: payload on **stdin** in a throwaway git repo
(the production path, motivated by a real prior shipped bug), direct unit assertions on both
importable libs, red-then-green ordering that honours "never edit tests and implementation in the
same step", the accepted-open shapes given failing-test coverage so closing one is deliberate, and a
first-arming check (task 13) born from `judge-guard` shipping with no `lib/` in the installed copy.
Task 8 as its **own behaviour-neutral commit** is exactly right.

What is wrong is the inventory task 8 operates on. The spec says "9 shell pairs and 1 Python pair"
(spec:55–57) and task 8 says "all **10** existing suites"; `CODING_MEMORY.md` at `1859c30` calls
this "pair count re-measured". Measured from `git ls-files`:

```
conforming pairs = 11   (10 shell + 1 python)
orphan suites    =  2
total suites     = 13
```

Three consequences, in ascending severity:

- **Undercount.** `panes/adapters/cmux-layout.sh` ↔ `.test.sh` is a real pair in a subdirectory the
  scope line never names. Miss a suite in the wiring and its subject becomes permanently
  unommittable behind `MSG_NO_MARKER` pointing at a suite that writes no marker.
- **The call site does not resolve.** `python3 "$(dirname "$0")/lib/write-test-marker.py"` is
  correct for `hooks/*.test.sh` (5 suites). For `panes/*` it resolves to `panes/lib/…`; for
  `panes/adapters/*` to `panes/adapters/lib/…`; for `statusline-command.test.sh` to `./lib/…`; and
  it is a shell snippet offered to a Python suite. With the mandated `|| exit 1`, **8 of 13 suites
  turn red on task 8**. Recoverable, but it is direct evidence the snippet was never checked
  against the layout.
- **Two suites have no sibling subject, and the design has no behaviour for that case.**

```
panes/adapters.test.sh            -> derives 'panes/adapters.sh'          (does not exist; it tests the adapters/ DIRECTORY)
panes/adapters/cmux-exec.test.sh  -> derives 'panes/adapters/cmux-exec.sh' (does not exist; it tests cmux.sh, 18.6K)
```

The spec carefully handles a subject with no test ("the gate never demands a test that does not
exist", spec:63) and never considers the converse. Under the design as written: the writer's
`git hash-object` of a nonexistent subject fails → `|| exit 1` → **a green suite now fails**; and on
the gate side, committing either test file derives an ABSENT subject → per the half-a-pair rule
(spec:221–226) → an **unsatisfiable block on two tracked files**, escapable only by `TEST_EXEMPT`
every single time. A control that mandates a routine bypass teaches the bypass.

This is not re-opening the ratified strict-1:1 decision. 1:1 is the right rule. The defect is that
the spec asserts the repo already conforms to it when 2 of 13 suites do not, and defines no
behaviour for the non-conforming case.

**And the coverage illusion underneath it:** because `cmux-exec.test.sh` is misnamed relative to its
subject, `panes/adapters/cmux.sh` — the largest adapter in the repo — reads as "a file with no
sibling test" and is **gated by nothing**, while the spec's coverage sentence tells the reader
`panes/` is covered. The gate would be green on a file it never checks.

**Overall risk: high.** Not because anything shipped, but because the design as written would produce

**Confidence: high.** Full spec read; pathspec and `-a` collection behaviour reproduced directly on
git 2.50.1; pair inventory enumerated from `git ls-files` rather than from the spec's claim.

## Concerns

1. `git commit -- <path>` commits worktree content; the table routes it to the index → silent
   fail-open in this repo's mandated commit form. Verified on git 2.50.1.
2. Pathspec also narrows the commit set; an index-based collector over-collects → false blocks on
   files not being committed.
3. The "`git commit -a` does not escape the gate" scenario is unreachable: `-a` branches the hash
   source but not the path set, and `git diff --cached` is empty for never-staged modifications →
   no pairs → allow.
4. Git-subsystem failure appears in neither the blocking nor the accepted-open list; a failed path
   collection is indistinguishable from a legitimate "no pairs" → allow. Same class as
   `judge-guard` fail-open #3, in the one subsystem that is new.
5. Repo-root/cwd resolution unspecified for `cd /other/repo && git commit …` — the hook may read a
   different repo's index and markers.
6. Pair inventory is wrong: 13 tracked suites, 11 conforming pairs (10 shell + 1 python), not 10.
   `CODING_MEMORY.md` calls this figure "re-measured".
7. Two suites have no sibling subject (`panes/adapters.test.sh`,
   `panes/adapters/cmux-exec.test.sh`); undefined behaviour → the writer fails a green suite, and
   the gate raises an unsatisfiable block escapable only by routine `TEST_EXEMPT`.
8. `panes/adapters/cmux.sh` (18.6K) is gated by nothing because its suite is named
   `cmux-exec.test.sh` — a coverage illusion the spec's scope sentence actively reinforces.
9. Call-site snippet `$(dirname "$0")/lib/write-test-marker.py` resolves for 5 of 13 suites; with
   the mandated `|| exit 1` the other 8 turn red on task 8.
10. Block-reason constants required but not enumerated: 5 named, ≥8 doors implied; the 2-mutant
    minimum cannot establish distinguishability across them.
11. Marker key normalisation from `$0` undefined — a suite run from a subdirectory may write a key
    the gate never looks up, yielding `MSG_NO_MARKER` right after a green run.
12. `TEST_EXEMPT` "logged" has no persistent destination; on this gate exemptions will be routine,
    and erosion will be unauditable.
