## What was changed

The test suite for the statusline script has 68 checks. Nobody knows whether those checks can
actually fail — a check that can never fail passes for free and protects nothing. There is a
second-order tool (`statusline-command.falsify.py`) whose whole job is to answer that: it replays
the current suite against five old, known-broken versions of the script and confirms the suite
still catches each break.

That tool has been broken for months. It was checking *how many* tests pass on each old version — a
fact about the size of the suite, not about the bug. Every time someone added a test, the number
drifted and the tool lied.

Revision 3 of the spec replaces counting with naming: each old version declares *which specific
checks must fail on it* (`must_fail`), plus a few that *must still pass* (`must_pass`, so a version
that collapses entirely can't fake a pass). It adds a "vacuity ratchet": run the suite against a
deliberately useless script and record which checks still pass — that list may only ever shrink.

**Analogy.** The old harness was a fire drill that counted heads. Add staff, and the count is wrong
even though the drill worked. Revision 3 stops counting heads and starts naming names: "Dave from
accounts must leave the building." That fixes the drift. What I measured this round is that some of
the named people don't work here, and the "useless script" you're testing against isn't pinned down
tightly enough to be reproducible.

## Does it do what you wanted?

Mostly yes, and revision 3 is a real improvement on revision 2. All six round-2 items landed and
landed *with reasoning*, not as compliance. But three concrete artifacts in the spec do not survive
contact with the actual suite, and I measured all three:

### 1. The `must_pass` example names two assertions that do not exist

§3 shows `"must_pass": ["baseline-user-host", "dir-basename"]`. I dumped all 68 assertion
descriptions from a working-tree run. There is no user@host assertion and no directory-basename
assertion in the suite. The nearest real one is `baseline renders model and context-bar segments` —
and that **fails** on `f0902ed`, because that 2024-era script predates the context bar. It is
era noise, precisely the thing §3 exists to filter out.

This is the third revision running in which the spec's illustrative example turns out not to exist
in the suite (rev 1: description-string identity; rev 2: `esc-literal-inert` in both lists; rev 3:
these anchors). The design is being reasoned from a mental model of the suite rather than from the
suite. That is the single most useful thing I can tell you this round.

### 2. `must_pass` can be satisfied by a script that prints nothing — no cross-check exists

**Measured**, running the current 68-case suite against each historical blob and against stubs:

| script under test | passes |
|---|---|
| `f0902ed` | **19** / 68 |
| `925c310` | **20** / 68 |
| `29d6131` | 28 / 68 |
| `4d63b09` | 33 / 68 |
| `e882659` | 32 / 68 |
| silent stub (`#!/bin/bash; exit 0`) | **24** / 68 |
| one-line stub | 30–31 / 68 (see §3 below) |

Two facts fall out.

**(a) The two oldest versions pass *fewer* assertions than a script that produces no output at
all.** By the suite's own measure, `f0902ed` and `925c310` are already worse than silence. §3's
stated purpose — "proving a version is not simply failing wholesale" — is measurably false for
them: they *are* failing wholesale, 49 of 68. `must_pass` will still pass on them, so the check
will not notice.

**(b) 16 of `f0902ed`'s 19 passing assertions are also passed by the silent stub.** An author
following §3 as written picks "a small named list of assertions that must still pass" from a pool
of 19, of which 16 prove nothing — they pass against *anything*, including a script that outputs
nothing. `SIGNATURE_RESTS_ON_VACUOUS` (§6) guards `must_fail` only; there is no equivalent rule
for `must_pass`.

The genuinely non-vacuous anchor pool — assertions that pass on a version and are passed by **no**
stub I could build — is this, and it is identical for all five versions:

```
* git repo -> git segment names the branch
* uncommitted changes -> dirty marker
* an over-wide segment survives intact on its own line   <- and this one falls to an echo-stdin stub
```

So `must_pass` is implementable, but it is 2–3 ids wide and says the same thing about every
version: *the script still runs and still renders a branch*. That is a liveness check, not an
anchor to a defect. Worth naming it that in the spec, so nobody later reads it as stronger evidence
than it is.

**Cheap fix, computable from data the harness already has in the same run:** make
`must_pass ∩ (any stub's vacuous list) ≠ ∅` a hard error, exit 2.

### 3. `STUB_ONE_LINE` is defined in prose, and prose does not pin bytes

§6 pins the number 30. **Measured, deterministic over 3 paired repetitions:**

```
#!/bin/bash                       #!/bin/bash
cat >/dev/null 2>&1               cat >/dev/null 2>&1
printf 'statusline\n'             printf 'statusline\n'
exit 0                            
-> 31 / 68                        -> 30 / 68
```

Both satisfy the spec's definition — "executable, exits `0`, writes one plain ASCII line". They
differ by a semantically redundant `exit 0`, and they differ by exactly one assertion
(`lock helpers behave correctly when called directly`). Neither is flaky: 6 runs of the first were
31/68 every time, 5 runs of the silent stub were 24/68 every time.

This is the **same species** as the 23-vs-24 discrepancy revision 3 went and reconciled, reappearing
one layer down on the second stub. The remedy in the spec ("recorded here so task 7 seeds from the
defined stub") does not work when "the defined stub" is a sentence. Put the literal stub bytes in
the spec in a fenced block and have the harness construct them from that literal.

Consequence if unfixed: task 1 seeds the list from whichever stub the implementer types. If they
type the 30-variant, `lock-helpers-direct` is left out of the list; a later trivial edit to that
stub flips it to passing and the ratchet fires **exit 1 / FALSIFICATION LOST** for a reason that has
nothing to do with falsification.

## Your pushback on signature/vacuity overlap — you are right, and I was overstated

You are correct and I withdraw the framing. `esc-literal-inert` failing on `f0902ed` (escapes
exceed the per-payload twin baseline) and passing against silence (0 ≤ 0) are both true. That is
not a contradiction, and "both lights green saying opposite things" was rhetoric, not analysis.
Classifying it as a **weakness** and ratcheting it via `SIGNATURE_RESTS_ON_VACUOUS` is the right
call — forbidding a legitimate state would have been worse than the problem.

**Where I still push back is the consequence, not the classification.** Measured: for `f0902ed`,
`literal \x1b in display_name stays inert` **and** `real ESC in display_name is stripped` both pass
against the silent stub. So **both** ids in the spec's own worked signature are overlap ids —
100% of that version's signature rests on evidence silence also satisfies. Under the design as
written, the harness prints `falsification intact`, exits `0`, and the only trace is two entries in
a list.

The fix is not "forbid overlap". It is a floor, and it is your own §9 reasoning applied one level
deeper — §9 already says the verdict must print `~11 of 68` so the line can't be read as a claim
about the whole suite. Same logic here:

- require **at least one non-overlap id per version's `must_fail`**, or
- print the per-version overlap fraction next to the verdict (`f0902ed: 2/2 signature ids rest on
  vacuous evidence`).

One more note on that ratchet: `SIGNATURE_RESTS_ON_VACUOUS` shrinks when the assertion is fixed
**or** when the id is deleted from `must_fail`. Deleting the id looks identical to progress. That is
the same shape as the empty-set-satisfies-subset bug §6 correctly fixes for the stub lists.

## Answers to your three questions

**Does `must_pass` close the era-noise gap?** Partially, and thinner than the spec implies. It
closes it *in principle* — a wholesale-failing script fails the 2–3 non-vacuous anchors. But (a)
the anchor pool is 2–3 ids and identical across all five versions, so it carries no version-specific
information; (b) nothing stops the anchors being drawn from the 16 vacuous ids, in which case the
check is decorative; (c) the spec's worked example anchors don't exist. Yes, a version can satisfy
both lists while failing for the wrong reasons — that is exactly case (b).

**Is there a remaining path to exit 0 while proving nothing?** Four, measured or read off the spec:

1. `must_pass` anchors drawn from the vacuous pool (16 of `f0902ed`'s 19 passes qualify).
2. A version whose entire `must_fail` is overlap — true of `f0902ed` as specified today.
3. **Historical runs have no full-case-count check.** §6 adds it for stub runs only, with the
   correct reasoning ("a subset check is satisfied by the empty set"). The analogue for a version
   run is "a `must_fail` check is satisfied by an early crash": if the suite dies after the named
   ids have emitted, everything named is satisfied and the harness exits 0 having run a fraction.
   Extend the full-count assertion to every run, not just stub runs. Free.
4. §5's flowchart covers "id named in a signature"; it does not say whether an absent **`must_pass`**
   id is exit 2 (missing) or silently satisfied (didn't fail). Write the safe reading down.

Also worth pre-empting for task 4: the spec says `4d63b09` "fails nothing today", true of the
20-case era. Against today's 68-case suite it fails **35**, all era noise. An implementer who runs
first will see 35 candidate ids and can satisfy §4 without adding a detecting assertion. §8
(reason before running) is the only guard and it is discipline, not a check.

**Do two stubs suffice?** Measured — essentially yes, and I could not build a third that earns its
keep. I tried six more shapes; every one passes *fewer* than the one-line stub and their pass-sets
are subsets of `SILENT ∪ ONE_LINE`, with a single exception:

| stub shape | passes | adds |
|---|---|---|
| 80-column single line | 28 | nothing |
| 500-column single line | 28 | nothing |
| realistic constant (`user@host  claude  git:(main)`) | 28 | nothing |
| echo stdin back | 29 | **1** id — `an over-wide segment survives intact on its own line` |

Note the realistic-looking stub — the "script silently ignores its input" shape, arguably the most
likely real breakage — adds **zero** ids over a stub that prints `x`. The one-line stub is the
high-water mark. Union of everything trivial I could construct: 31 ids; your two stubs cover 30 of
them. My recommendation is to keep two, and state in §6 that "non-vacuous" means "not satisfied by
*these two named stubs*" rather than "not vacuous" — because the real remaining gap is not a third
stub, it is that the ratchet cannot catch an assertion with slack against a *mutant of the real
script*, which is the exact defect class PR #43 shipped (a row-count bound with two rows of slack).

2. Add `must_pass ∩ vacuous = ∅` as exit 2, and a per-version non-overlap floor for `must_fail`.
3. Put both stubs in the spec as literal bytes, not prose. Then re-state the numbers.
4. Extend the full-case-count assertion to historical runs, not just stub runs.

None of these change the design's shape. They are pre-implementation edits to a spec that is
otherwise in good order.
