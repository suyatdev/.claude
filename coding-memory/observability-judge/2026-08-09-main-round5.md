## What was changed

The statusline script has a 68-check test suite. Nobody could prove those checks can actually
fail, and a check that cannot fail guards nothing. A second tool replays today's suite against
five old, known-broken versions of the script to prove the suite still catches each break.

Round 4 found a hole: you can quietly loosen a check by 8 bytes and every alarm stays silent.
**Revision 5 does not close that hole — it writes it down as a deliberate limit**, with the working
exploit, and hands it to a follow-up task. Alongside that it makes five repairs: the five old
scripts are now pinned by exact content fingerprint, "needs a human look" gets its own exit code
separate from "the tool is broken", the suite size is computed rather than typed in, the success
banner now says *measured* instead of *intact*, and two arithmetic errors are corrected.

**Analogy.** Think of a smoke-alarm tester. Round 4 proved you could tape over one alarm's sensor
and the tester would still say "all alarms working". Revision 5 doesn't remove the tape — it puts a
sign on the panel saying "this tester does not check sensor sensitivity", and changes the green
light's label from ALL SAFE to CHECKED WHAT I CHECK. That is the honest call, and I'd make the same
one. What I found this round is that **two of the new repairs each introduced a new fault of about
the same size as the one they fixed.**

## 🔴 Lead finding — the new exit code files the *worst* failure under the *calmest* label

This is the one that matters, and it is my own round-4 recommendation biting back.

Closure fails in two directions, and §5 gives both the same code:

- an **unpinned** id starts discriminating → genuinely review-needed, routine, ~22% of new tests;
- a **pinned** id **stops** discriminating → the assertion now returns the same verdict on all five
  broken versions. It detects nothing. That is a total detection loss.

Precedence is `2 > 3 > 1 > 0`. A pinned id that stops discriminating **necessarily** also mismatches
its row (the row was non-constant, now it is constant), so both the exit-1 and exit-3 conditions
fire — and precedence sends it to **3, REVIEW NEEDED**, whose §5 gloss is *"it is not an error: the
harness ran correctly and found a legitimate change that a human must classify"*.

**Measured, not argued.** I re-ran round 4's ord-66 hollow-out against the real suite (`-eq 0` →
`-le 4` on the control-character-in-a-path check, `statusline-command.test.sh:834`):

| check | base | hollowed |
|---|---|---|
| working-tree floor | 68/68 | **68/68** |
| every run emits 68 | true | **true** |
| vacuity lists | 24 / 31 | **24 / 31, unchanged** |
| ord 66 row | `..PPP` | **`PPPPP`** — detects nothing |
| discriminating set | 15 | **14** — closure fails |
| exit-1 condition (row mismatch) | — | **fires** |
| exit-3 condition (closure) | — | **fires** |
| **reported** | — | **exit 3, REVIEW NEEDED** |

Round 4 credited closure with catching this attack. It still catches it — but revision 5 moved the
catch into the bucket explicitly designed to be the calm one, and my own round-4 argument for
creating exit 3 was *"an alert that fires for routine events gets muted."* Exit 3 will fire on
roughly one in five added tests. The one time it means a safety assertion was gutted, it will look
identical to a normal Tuesday.

**Answer to your Q4: the split is right, the partition is wrong.** Keep exit 3 — CI does need to
tell "someone added a discriminating test" from "extraction is broken". But split the closure check
by direction:

- `discriminating - pinned` (something new flips) → **exit 3**, REVIEW NEEDED. Benign, routine.
- `pinned - discriminating` (a pinned id went constant) → **exit 1**, FALSIFICATION LOST. It is
  already exit 1 by the row check; precedence is what steals it.

Two lines, and it makes precedence `2 > 3 > 1 > 0` safe, because 3 can then only mean the benign
direction. Emptying `FLIP_MATRIX` entirely is the same class — today that is also exit 3.

## 🔴 Second finding — §2's empty-column sentence is wrong again, and its own measurement disproves it

You corrected this paragraph in response to round 4. The **number** is right; the **explanation
attached to it is false**, and the false part is new this round.

> "What catches a wholesale collapse there is **§4's empty-column guard**, not the full-count
> assertion. Measured: a script that prints nothing still emits all 68 results and passes 24 of
> them, so the count is unchanged by total failure and cannot detect it — **the empty column is what
> trips.**" (§2, and it is labelled as confirmed against the measurement run)

**Measured: the empty column does not trip.** Against the silent stub, the 15 pinned ids read

```
silent stub    P P P P P P P P P P P . . P P     ← 13 of 15 PASS
f0902ed pinned . . . . . . . . . . P . . . .
```

A silent script passes **13 of the 15** pinned ids. `f0902ed`'s column is nowhere near empty, so the
empty-column guard is silent. What catches the collapse is **the matrix**, with **12 mismatches of
15** — which is precisely what I told you in round 4. The empty-column guard fires only for a
collapse into *output that fails everything*, not a collapse into *silence* — and the sentence's own
cited evidence (`silent+exit emitted 68 passes 24`) is the silence case.

There is a better idea buried here that the spec keeps missing: **a `.` entry is an anchor too.** It
asserts "this assertion must FAIL on this version", and a collapse into silence makes vacuous
assertions *pass*, breaking those `.` entries en masse. So `f0902ed`'s "1/15 P is thin" framing
mis-locates the anchoring entirely — the anchor there is its **fourteen dots**, not its single P.
That is a stronger claim than the one the spec is trying to make, and it is true.

**A related ambiguity that has to be resolved in the same edit:** §4 never says whether the
empty-column guard reads the **recorded matrix** (a static typo check on the literal) or the
**measured results**. §2 needs the measured reading; §4's wording and the flowchart's node B (which
groups it with blob SHAs and row formats — all static) both read static. If it is static, it can
*never* fire on a collapse and §2's sentence is wrong a third way. One sentence.

## Your Q1 — I attacked the new surfaces. Three more paths, all new

### A. The vacuity lists have no membership check — the matrix does

§5 makes "the matrix names an id not in the suite" a hard error. **Nothing equivalent exists for the
two vacuity lists.** The only assertion is `passing ⊆ listed`, which is satisfied forever by a list
full of dead ids.

Path to exit 0 while proving nothing:

1. Delete a vacuous assertion. Its id stays in `VACUOUS_AGAINST_SILENT` — nothing notices.
2. Later, add a **new** vacuous assertion under that same id (§1's loop rule makes this natural:
   `pwd-fallback-empty-object` is tied to a payload, and changing the payload while keeping the
   suffix keeps the id).
3. `passing ⊆ listed` holds — the id was already listed. **The ratchet does not fire. Exit 0.**

"Ids are never reused" is prose in §1 and is unenforceable. The fix is one line and is symmetric
with the matrix's existing check: **every id in either vacuity list must be present in the run's
emitted id set, or exit 2.** Free.

### B. Duplicate keys in the matrix literal collapse silently — Defect 1, one level up

§2's row contract says the key must be "unique (§1)". §1's uniqueness check is about *the suite
emitting an id twice*. A duplicate key **in the `FLIP_MATRIX` dict literal** is a different thing
entirely, and Python swallows it. Demonstrated:

```python
FLIP_MATRIX = {
    "esc-real-stripped": "..PPP",   # what a reviewer reads
    "pwd-fallthrough":   "PP.P.",
    "esc-real-stripped": ".PPPP",   # ... and what silently wins
}
# rows a human counts in the source: 3
# rows the harness sees: 2
# esc-real-stripped compared against: .PPPP
```

So the file can say one thing and the harness compare against another — **exactly Defect 1** (the
docstring saying `9/20` while `EXPECTED` runs), reintroduced inside the artifact whose purpose is
deleting it. No linter is in the pinned toolchain to catch it. Fix: build the matrix from a list of
`(id, row)` tuples and reject a repeated id at load, or assert `len(FLIP_MATRIX)` equals the row
count. The row contract's "unique" rule as written **cannot fail** in a dict literal.

### C. "fewer than the full case count" writes one of three forgery nets out of existence

§5's exit-2 condition is *"a run emitted **fewer than** the full case count"*. Round 4 measured a
result-line forgery that produces **more**. I re-measured it against the live suite: a script whose
output is interpolated into a `bad "... $OUT"` diagnostic put forged result lines at column 0 —
**102 parsed lines instead of 68, 34 of them forged**.

Under the literal wording, 102 > 68 does not fire. Round 4 credited full-count as one of three
redundant nets against forgery; the duplicate-id and closure nets survive, so the design still fails
closed — but the redundancy was the point. **Change "fewer than" to "not exactly".** One word.

### D. The derived case count — the fix works, but it silently drops the check's only value

You adopted my round-4 recommendation to derive `N = len(working_tree_results)`. That is right and it
kills Defect 1. But round 4 also said the full-count check's *real* value is catching silent
assertion deletion — and **deriving N removes that**, because N moves with the deletion. Measured
consequence: delete a non-pinned assertion and the floor run yields 67, every run yields 67, floor is
all-pass, closure is unchanged → **exit 0**. That is fine for the 53 that prove nothing about these
defects, and it is *not* fine silently: 35 constant-fail ids include real safety assertions that
simply never passed on any historical version. The trade is correct; it is not written down. One
sentence in §2.

### E. What I could not break

Credit where it is due — these all fail closed, verified:

- Blob-SHA pinning genuinely closes the rtk-proxy hole. `4d63b09`'s 15-vector is byte-identical to
  the working tree's, so the matrix alone could never have seen it; now two checks do.
- Row alphabet/width: a zero-width space survives whitespace stripping and trips the alphabet rule
  → exit 2. Fail-closed.
- The tally-forging stub (`999/999 passed`) still fools `falsify.py:80`'s first-match regex — but
  §2's derived count reads **result lines**, not the tally, so the new design sidesteps it. The old
  `suite produced no tally` path survives with no home in §5's table; see Q2.
- The stub bytes are pinned literally, so the 23/24 and 30/31 wobble cannot return.
