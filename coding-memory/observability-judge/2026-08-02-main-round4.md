## What was changed

A design document — no code yet. It specifies a `git commit` gate: a test suite that passes leaves a
small signed receipt naming the exact file contents it certified, and a hook refuses any commit whose
contents don't match a receipt. Round 4 added one new section, **"The command grammar"**, which
measures how `git commit` actually parses its own arguments, and made seven surgical corrections to
round 3's findings.

## What could go wrong / what I'm unsure about

### 🔴 The sixth fail-open exists, and it is total (`success_masking = fail`)

You asked me to assume one. It is not in the grammar — it is upstream of it.

`settings.json:13` registers `rtk hook claude` as the **first** PreToolUse `Bash` hook, ahead of
`git-guard`, `doc-guard`, `judge-guard`, `merge-guard`. Measured live on this machine:

```
in : {"tool_name":"Bash","tool_input":{"command":"git commit -m test"}}
out: {"updatedInput":{"command":"rtk git commit -m test"}}
```

Every one of the sibling guards already handles this, and says so in its own comments:

- `git-guard.sh:16-18` — *"Must also catch the `rtk git ...` form: the RTK PreToolUse hook (registered
  ahead of this one in settings.json) rewrites plain git commands before this guard runs, so the
  command it sees may already carry an `rtk ` prefix."* → strips it at line 57-61.
- `doc-guard.sh:116-121` — same strip, same comment.
- **`classify-pr-command.py:32-39`** — the file this spec names as its own architectural model — carries
  `WRAPPERS = ("rtk", "time", "eval", "command", "builtin", "exec", "nohup")`, stripped in a loop,
  recorded in **ADR 0012**.

The spec mentions `rtk` **zero times**. Worse, it never defines the `kind: COMMIT` predicate at all —
the grammar section specifies flag/operand lexing to the exit code, but nowhere states how the
classifier decides a command *is* a `git commit`. Its accepted-open list says *"the `sudo`/`env`/`timeout`
wrapper denylist gap"*, which is lifted from `classify-pr-command.py`'s note about what is **not** in
`WRAPPERS` — inheriting the caveat while dropping the mechanism it qualifies.

**Why this is masking and not just an omission:** checklist task 14 (the first-arming check) says
*"pipe a real `git commit` payload into the installed hook and expect a readable exit 2"*. Hand-written,
that payload reads `git commit …` and the check goes green. In production the payload reads
`rtk git commit …`, the classifier answers `OTHER`, and the hook allows. A gate that looks armed and
passes everything — `judge-guard.sh:204` records that exact shape, and the spec quotes it.

### 🔴 Rule 2 of the new grammar recreates the G2 fail-open, unpinned

Rule 1 is carefully qualified: *"the first flag **that takes a value**…"*. Rule 2 is not:
*"`--opt value` consumes the next token."* Applied literally to a boolean long option, the next token
— which may be the only pathspec — is eaten, the form degrades `PATHSPEC → PLAIN`, and the gate hashes
the index while the commit ships the worktree. Measured:

| command | git ships | rule-2-literal form |
|---|---|---|
| `git commit -m msg --no-verify foo.sh` | `v3` (worktree) | `PLAIN` → hashes `v2` → **allows** |
| `git commit -m msg --signoff foo.sh` | `v3` | same |
| `git commit -m msg --no-status foo.sh` | `v3` | same |
| `git commit -m msg --no-all foo.sh` | `v3` | same |

A careful implementer would scope rule 2 by "value-taking flags must be known by name". Nothing pins
that reading: there is no G-row for a boolean long option adjacent to a pathspec, and the test list
(*"one case per grammar row G1-G9 … every value-taking flag in both groups"*) has no case for it. The
two-group list itself I checked against `git commit -h` — **it is exactly right, all 14 value-taking
flags, both optional-attached ones**. The defect is the unqualified sentence above it, not the list.

### 🟠 Long-option abbreviation walks past the `INCLUDE` refusal and the amend base

Git accepts unique-prefix long options. Measured:

- `--includ`, `--inclu`, `--incl`, `--inc` **all behave as `--include`** — rc=0, and each commits the
  staged `a.sh` at `v2` alongside the named path, which is M3 verbatim. `--in` and `--i` are ambiguous
  (rc=129). So the round-3 `MSG_UNSUPPORTED_FORM` door closes **only the fully-spelled form**; four
  spellings re-open the fail-open it was created for.
- `--pathspec-from-f` = `--pathspec-from-file`, same gap.
- `--amen`, `--ame`, `--am` **all mean `--amend`** (verified: HEAD replaced, rev-count unchanged). A
  classifier matching the literal `--amend` reports `amend: false`, leaves `<base>` at `HEAD` instead
  of `HEAD^`, and misses every pair carried in from the amended commit.
- `--all` is safe — `--al` is ambiguous, so there is no shorter spelling.

### 🟠 Two unlisted "the user picks the contents" forms

`-p/--patch` and `--interactive` both mutate the index **after** the hook has run. Measured:
`git commit -p` committed `bar.md` and `foo.sh` from an interactive selection; `--interactive` ran to
rc=0. Under the spec's rule 4 both classify `PLAIN`, so the gate hashes a pre-command index against a
commit that ships something else. The spec refuses `-i` — its immediate neighbour in `git commit -h`
— but never names these two, in the form table or the accepted-open list.

Minor and in the other direction: `-o/--only` with **no** operand exits 128 (*"No paths with
--include/--only does not make sense"*), but rule 4 routes it to `PLAIN`, so the gate may raise a
spurious block on a command git will refuse anyway — inconsistent with the `INVALID` principle
("git refuses it, so the hook allows").

### 🟠 Small factual slips in text presented as measured

- Line 550: *"outside a repo, `git diff --cached --name-only` prints nothing on stdout and **exits 128**"*.
  Measured: **129**, from `/tmp` and from `/`, with and without `HEAD`. The conclusion (non-zero, empty
  stdout, indistinguishable to a stdout-only reader) is unaffected; the number is wrong.
- **`G10` does not exist.** Line 648 cites *"measured G10"* and your brief describes *"ten measured rows
  G1-G10"*, but the grammar table stops at **G9**, and both the test list and checklist task 2 say
  "G1-G9". No coverage is lost — the unborn-HEAD measurement has its own scenario — but a dangling
  identifier in the one section whose authority is its numbering is a traceability defect, and the fact
  that you believe there are ten rows is the tell.
- `python3 -I` startup measured **29 ms** here against the doc's inherited *"≥56 ms"*. Different method
  (mine amortises a loop), and task 10 re-measures, so it changes nothing — but the figure should be
  re-derived, not carried.

### 🟠 An unnamed revert pair that is worse than the named one

The 5↔8 correction is right (task 5 is the writer; reverting it without 8 leaves 14 suites calling a
deleted file). But **7↔13 is unnamed**: task 13 registers the hook in `settings.json`, task 7 creates
it. Reverting 7 alone afterwards leaves a registration pointing at a missing script — and by this
repo's own documentation (`git-guard.sh:22-25`, *"a dead script exits non-zero, which PreToolUse reads
as a block"*) that blocks **every Bash call in the session**, not just commits. That is a worse blast
radius than the pair the document does warn about.

### 🟡 The exemption log promises an audit it cannot deliver

§Exemption logging argues that stderr alone is insufficient because *"an unauditable exemption count is
the exact erosion path the control exists to prevent"*, then puts the log at
`<repo>/hooks/state/test-exempt.log` — inside the tree `.gitignore:17` covers, at mode 0700. It is
local-only and invisible to any reviewer or any other machine. It defeats *self*-deception, which is
worth something; it does not deliver the auditability the paragraph claims.

### On observability of the control itself — this part is good

`--status` printing ACTIVE/INERT plus the resolved toplevel, run first in task 14, closes round 3's
finding properly and rejects per-commit chatter for the right reason. All **14 doors appear in the
flowchart** and each carries a distinct constant; `MSG_NO_MARKER` derives `bash`/`python3` from the
suite extension. An engineer who hits a block can name the door and the remedy without opening the
source. The one gap: blocks are not logged anywhere, so there is no after-the-fact record of *how
often* the gate fires — only of when it was bypassed, and that record is untracked (above).

## What I'd double-check before merging

1. **Whether subsequent PreToolUse hooks receive rtk's `updatedInput`.** Three sibling guards assert in
   comments that they do and strip accordingly, which is strong corroboration — but confirm it against
   the harness, because the whole control is live or dead on that answer. Then decide explicitly where
   wrapper stripping belongs, and state how `kind: COMMIT` is decided at all.
2. **Re-derive the grammar from `git commit -h`, not from remembered shapes.** The two-group value-flag
   list is already exactly right; what is missing is a stance on tokens the list does not contain —
   boolean long options, `--no-*` negations, unique-prefix abbreviations, unrecognised options. A
   fail-closed default for anything unrecognised would collapse four of my findings into one rule.
3. **Add G-rows and test cases for the four shapes above**, since the test plan is derived row-by-row
   from the G-table; a shape with no row gets no mutant and no assertion. The 24-mutant floor is counted
   off a door/allow list that is itself short by at least three allow paths.
4. **Task 14 must pipe the payload the harness actually produces**, not a hand-written ideal one.
5. **Name 7↔13 as a revert pair** alongside 5↔8.
6. Fix `G10`, the 128→129 exit code, and decide whether the exemption log should live somewhere a
   reviewer can see.
