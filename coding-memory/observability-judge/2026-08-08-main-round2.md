## What was changed

Still a spec, no code. It rewires the "test-of-tests" that proves the statusline suite is capable of
failing at all. Revision 2 answers both round-1 findings with real mechanisms rather than wording:

1. **Case identity now exists.** Every assertion gets a stable kebab-case id, printed on *both* pass
   and fail (`ok [id] — …` / `FAIL [id] — …`), passed as the **first argument** of `ok()`/`bad()` so
   a call site physically cannot emit a line without one. This was round 1's unimplementable-as-written
   blocker; it is now implementable. Good design instinct — enforcement by construction, not by rule.
2. **An empty signature is a hard error** (§3), closing the `4d63b09` hole where a version's
   `must_fail` list was empty and therefore satisfied by literally any input.
3. **A vacuity ratchet** (§5): run the suite against a stub script, record which assertions still
   pass, and require that set to be a **subset** of a checked-in `KNOWN_VACUOUS` list.

Analogy: the smoke detector now has a serial number on every unit (fix 1), you can't sign off an
empty inspection sheet (fix 2), and there's a list of detectors known to be duds that may only get
shorter (fix 3). What follows is about whether the dud list actually helps.

## Does it do what was intended?

**Fixes 1 and 2: yes, cleanly.** Both round-1 findings are properly addressed, not papered over.

**Fix 3: it is not a rubber stamp, but it does not close `success_masking` — it relocates it.**
That was the headline question and the answer is measured, below.

## Q1 — Does the ratchet close `success_masking`, or relocate it?

**Lead finding: the signature list and the vacuous list are drawn from the same pool, and the design
never cross-references them. The spec contradicts itself on the same page.**

§2's only worked signature:

```python
"f0902ed": {"must_fail": ["esc-literal-inert", "esc-real-stripped"]}
```

§5's only worked `KNOWN_VACUOUS`:

```python
KNOWN_VACUOUS = ["esc-literal-inert", "pwd-fallthrough-stripped", ...]
```

`esc-literal-inert` appears in both. The same id is simultaneously *"the assertion that proves
`f0902ed`'s defect is still detected"* and *"an assertion that cannot fail for the reason it claims."*
**Both checks go green and the harness exits 0.**

This is not a typo in the examples — it is structural. Measured against the spec's own stub, the
24 passing assertions include **all six `assert_no_injection` cases, all four `$PWD fallback stripped`
cases**, `all-control cwd falls through to a stripped $PWD`, and `a control character in a path never
reaches the output`. That family is precisely where the ~11 signature ids must come from, because it
is the only family that discriminates between the five historical versions. So the overlap is close
to total by construction, not by accident.

The mechanism is `assert_no_injection` (`statusline-command.test.sh:547-562`), which computes its
own ceiling from a benign twin render:

```bash
limit="$(count_byte "$(render "$3")" '\033')"   # twin: 0 bytes if the script outputs nothing
out="$(render "$2")"
esc="$(count_byte "$out" '\033')"               # hostile: also 0
if [ "$esc" -le "$limit" ] && [ "$nl" -eq 0 ] && [ "$bel" -eq 0 ] && [ "$cr" -eq 0 ]; then
```

Under silence the comparison degenerates to `0 <= 0` and the assertion passes for free. The twin
design is genuinely clever — it is what stops the baseline drifting as segments are added — but it
has no floor.

**To be fair to the design:** `esc-literal-inert` is *not* useless. It does fail on `f0902ed`, which
emits a real escape. Its passing is *conditionally* meaningful — meaningful against a script that
produces output, meaningless against one that doesn't. The flaw is that nothing in the harness tells
the reader which condition held, and the two lists assert opposite things about the same id with no
check between them.

**Is a seeded-at-23 ratchet meaningfully different from a rubber stamp? Yes, but less than the spec
implies.** Honest split:

*Genuinely new and worth having:* it is monotone. A newly-written vacuous assertion fails the harness
the first time it runs. Three of the four defects the judge found during PR #43 were exactly that
class, so stopping the inflow has real value, and it is value nothing else in this repo provides.

*Where it falls short of the framing:*
- It **certifies the current 24 as acceptable**, and the harness still prints `falsification intact`.
  A third of the suite, including every safety-critical assertion, cannot fail — and the green light
  does not change shade.
- There is **no forcing function**. "Expected to fall" is a hope. §8 already concedes the harness runs
  by human memory, the mechanism that already failed once. A list that may only shrink, with nothing
  causing it to shrink, sits at 24 indefinitely.
- **No cross-check** with the signatures (above).

The missing piece is one line: intersect `must_fail` with `KNOWN_VACUOUS` and at minimum print it —
*"this version's defect is detected only by assertions that can pass for free."* Hard-erroring would
be stronger; printing it would at least stop `falsification intact` reading as more than it means.

## Q2 — Is there a fourth state that exits 0 while proving nothing?

Yes — four candidates. The first two are the ones I would act on.

**(a) `KNOWN_VACUOUS` overlap — demonstrated above.** Exit 0, both arms green, signatures composed of
assertions the same run records as satisfiable by silence.

**(b) Subset-of-a-set is satisfied by the empty set — the same shape §3 just made a hard error.**
§5 says *"the set passing against the stub must be a subset of `KNOWN_VACUOUS`"* and *"shrinking is
always allowed and needs no edit."* If the stub run degrades — suite aborts early under `set -u`
(`statusline-command.test.sh:24`), `mktemp -d` fails, git is unavailable for the git-segment cases —
fewer `ok` lines are emitted, the passing set shrinks, and **the ratchet reads a broken run as
progress.** The spec closed exactly this shape in §3 ("an empty list is satisfied by any input") and
reproduced it in §5.

*Stated honestly: I could not realise this with a simple stub.* Silence, exit 0, NUL bytes, and 200 KB
of garbage all held the tally at 68. So this is a design-hardening item, not a demonstrated bug. The
fix is symmetric with §3 and costs one line: assert the stub run's **total** equals the working-tree
total, and hard-error otherwise. Had I been able to realise it, this dimension would read `fail`.

**(c) A duplicated or swapped id — see Q4.** Both exit 0. Both defeat the spec's stated mitigation.

**(d) Stream merging.** §1 specifies the parse regex but **never says which stream it parses.** The
suite deliberately does not swallow the script's stderr (`statusline-command.test.sh:46-48` — "a jq
parse error here would otherwise be invisible"), so the script under test writes directly into the
suite's stderr. Today `falsify.py:76-79` reads `proc.stdout` only, so the path is closed. But nothing
in the spec pins that, and merging streams is the natural thing an implementer does when adding
diagnostics. Verified: a stub printing `FAIL — forged` to stderr puts 108 `FAIL`-prefixed lines into a
combined stream. Low likelihood, near-zero cost to pin — one sentence in §1.

## Q3 — Is "executable, exits 0, writes nothing to stdout" the right stub?

**No. It under-detects, measurably — and the spec's own seed number does not match it.**

| stub | assertions passing (of 68) |
|---|---|
| silence, `exit 1` (round 1's stub, source of the spec's "23") | **23** |
| silence, `exit 0` (**the stub §5 actually defines**) | **24** |
| 200 KB of garbage on stdout | 29 |
| a single constant benign line — `printf "x\n"` | **30** |

Two separate problems.

**1. The spec's seed is wrong for the stub the spec defines.** §Background Defect 2 and §5 both say
23; the stub §5 defines produces **24**. The extra one is `lock helpers behave correctly when called
directly`, which is exit-status-sensitive. This matters more than an off-by-one: task 7 says *"seed
`KNOWN_VACUOUS` from measurement"* while §Risk says *never re-baseline*. An implementer who measures
24 against a spec that says 23 must treat that as a **finding**, not quietly write 24 down. The spec
doesn't flag that its two numbers came from two different stubs, so the discrepancy will look like
noise at exactly the moment the discipline matters.

**2. Silence is the weakest detector in its own family.** A stub emitting one constant harmless line
is satisfied by **30** assertions — six more than the ratchet will ever see. The escapees:

```
absent COLUMNS falls back to one line
degenerate COLUMNS '-1' / '' / '0' / 'abc' falls back to one line   (4 cases)
wide terminal renders a single line
non-integer token count does not crash the render
```

That last one is `if [ -n "$OUT" ]` (`statusline-command.test.sh:155`) — satisfied by *any* non-empty
output. These are textbook vacuous assertions of the weakest shape in the suite ("output exists" /
"output is one line"), and **the ratchet will certify all seven as non-vacuous, permanently.**

That is the precise sense in which the ratchet relocates rather than closes: it defines vacuity as
*"passes against silence"*, but the class the harness exists to catch is *"cannot fail for the reason
it claims."* The first is a proper subset of the second.

A constant-output stub is also the **more realistic broken script** — real regressions usually still
emit something; total silence is the rare case. Recommendation: run **both** stubs with one
`KNOWN_VACUOUS` list per stub. ~5 extra lines, +6 detections, no new concepts.

**Over-detection, the other direction:** some entries can never leave the list. Assertions that
legitimately assert an *absence* — `a control-character path resolves to no repo, so no git or wt
segment`, `the main worktree shows no wt:() segment` — cannot distinguish "no segment" from "no
output" without a paired positive control. They will sit in `KNOWN_VACUOUS` forever. The list will
therefore mix "vacuous, fix me" with "asserts an absence, working as intended", and the design gives
no way to tell them apart. Over time that erodes the list's meaning — the standard fate of a
suppression file without categories. Cheap fix: a one-word tag per entry.

## Q4 — Risk in the ~68 mechanical id edits that the spec has not named

The spec names one risk ("a typo silently renaming a case") and one mitigation ("§4's exit-2 path is
what catches it, because every signature id must resolve"). **Measured, the mitigation is weaker than
stated and the edit surface is larger than stated.**

**The edit count is understated by ~35%.** Not ~68 edits:

```
direct `ok "…"` call sites   : 45
direct `bad "…"` call sites  : 46      → 91 direct edits
wrapper helpers needing a new positional param : assert_bar (5→6),
  assert_sigma (3→4), assert_no_injection (3→4), plus render_cols/
  render_no_cols/widest_line call chains
```

68 is the number of *cases*; 91 is the number of *lines that must change*, plus every wrapper
signature and every wrapper call site. Roughly 45 of those are `if/ok else/bad` pairs where the same
id must be typed **twice, identically** — which is exactly the copy-paste context that produces
duplicate ids.

**Three failure modes the exit-2 mitigation does not catch:**

1. **A duplicate id** (likeliest mechanical error: copying an `if/else` block and not changing the id).
   Suppose signature id `X` appears at two sites. The real assertion **passes** — falsification lost —
   but the unrelated duplicate **fails**. The harness sees a `FAIL [X]` line, marks the signature
   satisfied, **exits 0**. Falsification lost, unreported. The ratchet meanwhile sees `X` in both the
   passing and failing sets, and the design does not say which wins. Task 2's uniqueness check is a
   one-time manual step; nothing makes the harness enforce uniqueness at runtime. It should — one line.
2. **A swapped pair of ids.** Both unique, both resolve, exit-2 never fires. The signature now names a
   different assertion than intended. Nothing catches it.
3. **Coverage.** Exit-2 only ever exercises the ~11 ids named in signatures. A typo in any of the
   other ~57 is completely unobserved — the id is unique, resolves to nothing, and nothing references it.

**A shifted positional argument is the silent one.** Under `set -u`, a *missing* argument errors
loudly (good). A *shifted* one does not: `assert_bar "$1 desc, $2 tokens, $3 colour, $4 fill, $5 label"`
gaining an id in position 1 renumbers everything behind it, and a mis-shift makes the assertion compare
the wrong things while still emitting a well-formed `ok [id]` line. **Task 2's only check is "the suite
still reports 68/68"** — which a shifted-but-still-passing assertion satisfies exactly. Green tests
hiding the problem, in the task designed to prevent it.

**Free invariant the spec should add to task 2:** run the stub *before* and *after* the id edit and
assert the vacuous set is **unchanged — same count, same ids**. The id edit is purely additive, so any
movement is a defect. That single check catches shifted arguments in the safety family, which
`68/68` cannot.

## Concerns

1. LEAD: signature ids and `KNOWN_VACUOUS` are drawn from the same pool with no cross-check — the spec's own §2 and §5 examples share `esc-literal-inert`. The harness exits 0 printing `falsification intact` on the strength of an assertion the same run records as satisfiable by silence.
2. MEASURED: the stub §5 defines (silence, exit 0) passes **24** of 68, not the 23 the spec seeds from — round 1's number came from an `exit 1` stub. Task 7 ("seed from measurement") meets §Risk ("never re-baseline") at exactly this discrepancy, and the spec does not flag it.
3. MEASURED: a constant-output stub (`printf "x\n"`) passes **30** of 68. Seven assertions of the form "output exists" / "output is one line" — including `non-integer token count does not crash the render` (`[ -n "$OUT" ]`, test.sh:155) — will be certified non-vacuous permanently. Silence is the weakest detector in its family and the less realistic broken script.
4. "Subset of `KNOWN_VACUOUS`" is satisfied by the empty set: a degraded stub run reads as progress. Structurally identical to the empty-`must_fail` hole §3 just made a hard error. NOT realisable with a simple stub (silence/NUL/200 KB garbage all held the tally at 68) — design-hardening, not a demonstrated bug.
5. MEASURED: the edit surface is 91 direct `ok`/`bad` call sites (45 + 46) plus 3 wrapper signatures, not "~68 mechanical edits". ~45 are `if/else` pairs requiring the same id typed twice.
6. The stated mitigation ("every signature id must resolve → exit 2") catches neither a duplicate id nor a swapped pair, and covers only the ~11 ids named in signatures — a typo in the other ~57 is unobserved. A duplicate id where the wrong site fails satisfies the signature and exits 0 with falsification lost.
7. Task 2's verification (`68/68`) cannot detect a shifted positional argument in a wrapper. Free fix: assert the stub's vacuous set is byte-identical before and after the id edit.
8. §1 specifies the parse regex but not the parse *stream*. The suite deliberately leaves the script's stderr unswallowed (test.sh:46-48); `falsify.py:76-79` reads stdout only today, but nothing pins it, and merging streams for diagnostics would let the script under test forge signature-satisfying lines.
9. `KNOWN_VACUOUS` will permanently contain absence-asserting cases (`the main worktree shows no wt:() segment`) that can never be "fixed" without a paired positive control, mixed indistinguishably with genuinely-broken entries. A one-word category tag per entry prevents the usual suppression-file rot.
10. Round-1 fix #1 (`must_pass` anchor) and #4 (state real coverage, ~11 of 68) dropped with no written rationale.
11. §Background Defect 1 still presents "lost exactly one pass, which growth alone cannot cause" as a "real unread signal". Round 1 disproved it: era-appropriate suites reproduce 9/10/15/20/19 exactly, and the flip is three benign token-bar cases against two gains — a net figure. Tasks 3/5 will re-derive a settled question.

## What I would fix before implementing

1. Intersect `must_fail` with `KNOWN_VACUOUS` and hard-error (or at minimum print it). Without it the two mechanisms certify opposite things about the same id and both read green.
2. Add a second stub (constant benign output) with its own list — ~5 lines, +6 detections.
3. Assert the stub run's total case count equals the working-tree total; hard-error otherwise. Symmetric with §3, closes the empty-set path.
4. Make the harness enforce id uniqueness at runtime, not just once by hand in task 2.
5. Add to task 2: the stub's vacuous set must be unchanged before and after the id edit. Catches shifted wrapper arguments that `68/68` cannot.
6. Reconcile 23 vs 24 in the spec text *before* task 7, so the implementer meets it as a known discrepancy rather than a re-baselining decision.
7. Pin the parse stream to stdout in §1.
8. Correct §Background Defect 1 to record round 1's resolution, and record why `must_pass` was dropped.
