## What was changed

A design document — still no code. It specifies a `git commit` gate: when a test suite passes it
leaves a small receipt naming the exact file contents it certified, and a hook refuses any commit
whose contents don't match a receipt. Revision 5 is a contract-totality round: it adds an 18-cell
`kind` × field matrix so every classifier output is defined (not just the `COMMIT` one), replaces
three disagreeing ABSENT probe tables with one semantic definition plus probes demoted to
implementations, reconciles the failure-door rows so each rule lives in exactly one table, mirrors
the Python call site against the shell one, and adds a third latency budget for payloads that
mention "commit" without being one.

For what revision 5 set out to do — yes, and the structural move is the right one. I re-measured

recurring defect class rather than to a defect.

## What could go wrong / what I'm unsure about

### 🔴 The `rtk` fail-open is still unwritten (`success_masking = fail`)

Verified independently, not taken from the round-4 verdict:

- `rtk` is installed: `/opt/homebrew/bin/rtk`.
- `settings.json` registers `rtk hook claude` as the **first** `PreToolUse`/`Bash` hook, ahead of
  `git-guard`, `doc-guard`, `judge-guard`, `merge-guard`.
- `RTK.md` (loaded into every session) states commands are rewritten, e.g. `git status` →
  `rtk git status`.
- `hooks/lib/shell_segments.py:34` carries `WRAPPERS = ("rtk", "time", "eval", "command", "builtin",
  "exec", "nohup")` and strips them at line 86 — the existing guards were built specifically to
  survive this.
- `grep -i rtk docs/features/verification-marker-gate.md` → **zero matches.**

There is a plausible accidental rescue: revision 5 blocks implementation on "the shared-lexer
decision landing in `shell_segments.py`", and that lexer already strips `rtk`. But an accidental
rescue is not a control. The spec still never defines the `kind: COMMIT` predicate, never names the
wrapper, and — decisively — **task 14, the check that exists precisely to catch "shipped and does
nothing", pipes only `git commit …` and `git commit -am msg` payloads.** Neither reproduces the
rewrite. A gate that is dead on arrival passes its own first-arming check, and `--status` prints
`ACTIVE` while every real commit sails through. That is `judge-guard.sh:204`'s own lesson happening
one level above where the spec quotes it.

### 🔴 The pair inventory is stale, and it drives a completion criterion

§Scope's table is honestly dated 2026-08-02 and was correct then. Three more conforming pairs landed
on **2026-08-03** in commit `ac5afa2`, one day before revision 5 was written:

- `hooks/git-guard.sh` ↔ `hooks/git-guard.test.sh`
- `hooks/doc-guard.sh` ↔ `hooks/doc-guard.test.sh`
- `hooks/lib/classify-git-command.py` ↔ `hooks/lib/classify-git-command.test.py`

Measured today from `git ls-files`: **14 pre-existing conforming pairs, not 11** (2 orphans
unchanged). So task 8's "**all 14 paired suites** — the 11 in §Scope's first table plus this
feature's own 3" is wrong; the real number is **17**. If task 8 is executed against the literal
list, those three suites go unwired, no marker is ever written for them, and `git-guard.sh`,
`doc-guard.sh` and `classify-git-command.py` — three of the most actively edited files in this
repo — become **uncommittable** the moment the gate arms, escapable only by `TEST_EXEMPT` on every
commit.

The design partly saves itself here, and this deserves credit: inventory assertion 1 is a
*property* ("every tracked pair's suite contains the marker-write call"), so it turns red at task 8
and forces the correction. That is exactly why the round-5 property-over-count reasoning was right.
The irony is that the same revision re-froze a literal count (`14`) in the prose and the checklist —
the precise mistake §"why not a count" spends four paragraphs diagnosing about round 2.

### 🟠 Option abbreviation is unaddressed and unmentioned

Round 4 raised it; revision 5 does not mention abbreviations at all. Re-measured on git 2.50.1:

| spelling | result |
|---|---|
| `--amen`, `--ame`, `--am` | **rc=0, commit lands** — all mean `--amend` |
| `--includ`, `--inclu`, `--incl`, `--inc` | accepted as `--include` (rc=128 only for the unrelated "No paths" reason) |
| `--pathspec-from-f` | rc=129 `option 'pathspec-from-file' requires a value` — accepted, just wants its value |

A classifier matching `--amend` literally leaves `<base>` at `HEAD` instead of `HEAD^` and misses
every pair carried by the amended commit — a silent fail-open. A classifier matching `--include`
literally lets `--incl -- b.md` walk straight past `MSG_UNSUPPORTED_FORM`, re-opening the M3
fail-open the spec measured and closed. Both are the same defect class as G1/G4, in a document whose
whole thesis is that a lexer must not handle only the spelling its author had in mind.

### 🟠 Two measurements that are wrong, in a document whose credibility is "measured, not recalled"

- **§"Which paths" / line 641:** "outside a repo, `git diff --cached --name-only` … exits 128."
  Measured today: **129**. (`rev-parse --show-toplevel` is 128, correctly.) The stated *rule*
  ("non-zero from any other collection command → `MSG_GIT_FAILED`") is unaffected, so the impact is
  reputational rather than behavioural — but round 4 flagged this exact cell and it survived.
- **§Latency:** "`python3` startup at **≥56 ms**". Measured here across 5 runs: **20–30 ms**. The new
  ≤80 ms budget is derived from the inflated figure, so it sits roughly 2.5× above the actual floor.
  A budget that cannot be exceeded is a budget task 10 cannot learn anything from — which is the
  same "green measurement that proves nothing" shape as the rest of this finding list.

### 🟠 The mutation floor is aimed away from the risk

24 mutants = 14 doors + 9 allow paths + 1 emptied classifier. All of that lives in the **hook**. The
two fail-opens this spec actually discovered by measurement (G1 bundle decomposition, G2 bare
operand) live in the **classifier's grammar**, which gets rich assertions but **no mutants**. The
spec's own justification for mutation testing is that `judge-guard` had 48 assertions that could not
tell one door from another — that argument applies with more force to the grammar, where a mutant
that widens `INVALID` or collapses `-am` back to `PLAIN` disables the gate for this repo's dominant
commit shapes.

### 🟡 Carried-over items still open from round 4

- **Revert-pair 7↔13 is still unnamed.** Task 8's revert analysis (5↔8) is good, but registering the
  hook in `settings.json` (task 13) while `test-marker-guard.sh` (task 7) is absent blocks **every
  Bash command**, per the fail-closed precedent the spec itself cites at `git-guard.sh`.
- **The exemption log is not auditable.** It lives at `<repo>/hooks/state/test-exempt.log`, under
  `.gitignore:17`, mode 0700, machine-local, deletable without trace. §Exemption logging argues
  correctly that "an unauditable exemption count is the exact erosion path the control exists to
  prevent" — and then specifies a store that delivers exactly that. On this gate exemptions will be
  routine.
- **`FOREIGN` false-blocks a same-repo `cd`.** `cd "$HOME/.claude" && git commit …` is a shape this
  session's own memory workflow uses. The cost is stated and `TEST_EXEMPT` now genuinely reaches it,
  so this is accepted rather than unknown — but it will convert into routine exemptions, which feeds
  the item above.
- **`hooks/lib/shell_segments.py` has no sibling test.** The file this feature's implementation is
  now *blocked on* is itself outside the gate's coverage and outside the sibling-test convention.
  Not a defect in this spec; worth naming, since the follow-up that unblocks task 2 lands in an
  ungated file.

## What I'd double-check before merging

1. **Write `rtk` into the spec.** Define the `kind: COMMIT` predicate explicitly, state that the
   classifier is built on `shell_segments.py` (or restates its `WRAPPERS` handling), and add
   `rtk git commit -m msg` and `rtk git commit -am msg` payloads to **task 14**. Without the task-14
   addition the fail-open stays undetectable even if it is accidentally fixed.
2. **Re-measure §Scope's pair table** and re-derive task 8's number from `git ls-files` at execution
   time rather than from a frozen literal — the property assertion is the criterion, so let the
   prose say `all tracked pairs` and drop the count.
3. **Add abbreviation handling** (prefix matching for `--amend`, `--include`, `--pathspec-from-file`)
   to the grammar section, with G-rows and test cases, or list them explicitly on the accepted-open
   list so the fail-open is a decision rather than an oversight.
4. **Fix the two numbers** (129, and the python3 startup figure) and re-derive the ≤80 ms budget from
   a figure measured on this machine.
5. **Extend the mutation floor to the classifier grammar** — at minimum one mutant each for bundle
   decomposition, the value-taking-flag list, and the `INVALID` predicate.
6. **Name the 7↔13 revert pair** in the checklist alongside 5↔8.
