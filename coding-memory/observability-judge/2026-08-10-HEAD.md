## What was changed

Nothing yet — this is a design. It fixes a lock that quietly stops locking.

`hooks/git-guard.sh` has two guards (don't commit source to `main`, don't force-push `main`). Both
ask one question first: *which branch am I on?* If you're on a "detached HEAD" — git's word for
standing on a specific commit instead of a named branch — git answers with the literal word `HEAD`.
The lock compares that to `main`, sees no match, decides "not my problem" and steps aside. **Both
guards go silent.** It already happened: the reflog shows a checkout of `origin/main` (which
detaches) followed straight by two commits onto `main` that the guard never inspected.

The fix: when the guard *can't tell* where it is, it now assumes the worst and blocks, instead of
assuming the best and waving you through. Like a night watchman who, when the ID scanner breaks,
stops letting everyone in.

## Does it do what you wanted?

Yes — the direction is right and the reasoning is unusually careful. It fixes the shared helper
rather than one call site (so the force-push half doesn't stay open), and it catches a second bug in
the same function: when git fails entirely the answer is `""`, which also read as "not main". I
verified both arms are genuinely reachable and distinguishable — outside a repo you really do get
`""`, detached you really do get `HEAD`.

**But it has a hole it doesn't know about.** A brand-new repo, freshly `git init`-ed with no commits
yet, *also* answers `HEAD`:

```
$ git init -q . && git rev-parse --abbrev-ref HEAD 2>/dev/null || echo ""
HEAD          # <-- not detached. Just has no commits yet.
```

So after this change, **the first source commit in any new repository gets blocked**, and
`git-guard.sh` has no bypass variable. The spec's Accepted-costs section states the opposite —
*"nothing that previously worked stops working"* — which is not true for this case.

Worse, the escape route the spec hands you doesn't work there. It says to run `git switch -c <branch>`.
I tried it on an unborn repo:

```
$ git switch -c feat/x        # on a fresh repo, no commits
$ git rev-parse --abbrev-ref HEAD   -> HEAD       # still blocked
$ git symbolic-ref --short HEAD     -> feat/x     # knows the answer perfectly well
```

This collides head-on with this repo's own `setting-up-a-new-project` gate. The only way out is an
obscure one (make the very first commit documentation-only with an explicit pathspec).

That last line is also the constructive fix: `git symbolic-ref --short HEAD` reads the HEAD ref
directly and needs none of the `main`/`origin/main` lookups the spec rightly rejected in its
"why not resolve the true position" argument. On a genuine detached HEAD it returns empty (→ still
fail closed, as intended); on an unborn branch it returns the real branch name. That's strictly
better on both axes, not a trade-off. The spec surveyed the *expensive* alternative and dismissed it
well, but never looked at the cheap one.

## What could go wrong / what I'm unsure about

**On your first question — are two reworded stderr messages enough instrumentation?** No.

1. **The messages never say what the guard actually saw.** All three rewrites are static strings that
   merge three different situations ("on main" / "detached" / "git broke") into one sentence. When
   this blocks you, you can't tell a true positive from a false one. One line fixes it: print the
   observed value — `checkout: HEAD (detached)` vs `checkout: <git could not answer>` vs
   `checkout: main`. That turns a fixed string into real instrumentation, at the only moment anyone
   is looking.
2. **The message table misses a fourth code path.** `git-guard.sh:164` prints *"nothing is staged yet,
   so this commit is judged by the paths it names"* — that path now fires for detached-HEAD commits
   (`--amend`, `-a`, bare `git commit` with an empty index) and talks only about pathspecs. The
   operator gets a lecture about `--` separators with no hint that detachment is why they're here.

**On your second question — is fail-closed + no bypass + no telemetry sound?** Fail-closed with no
bypass is the right call, and I'd resist adding a bypass variable: the legitimate escape
(`git switch -c`) is something you should be doing anyway, and a bypass var gets typed reflexively
until the guard means nothing. **I would not add a counter or log file.** This hook runs on every
single Bash call; a counter buys new file I/O, a new failure mode, and a log nobody reads. The
correct instrumentation for a guard like this is a self-explaining refusal at the moment it fires —
which loops back to point 1. Fix the message and you don't need telemetry. Leave the message vague
and a counter won't save you either.

**On your third question — can the 8 scenarios tell "works" from "over-blocks"?** Partly.
Genuinely good: the four regressions pin the real over-block risks, and the checklist demands the
new tests *fail first* and captures the output — that's the discipline that stops a test that tests
nothing. Scenario 4 also truly discriminates the `""` arm (I confirmed a non-repo yields `""`, so
omitting that arm would fail the test). Gaps: no unborn-HEAD scenario in either direction, so **the
whole suite can go green while the new-repo over-block ships**; and 3 of the 4 new scenarios assert
only the exit code, so a message could stay wrong and still pass.

## What I'd double-check before merging

1. Decide `symbolic-ref` vs. the proposed `case` form before writing code — it's a cheaper probe that
   removes the unborn-HEAD problem entirely. My pick: `symbolic-ref --short HEAD`, treating empty as
   cannot-tell → block.
2. Either way, add two unborn-HEAD scenarios (unborn `main` → block; unborn `feat/x` → allow).
3. Correct the Accepted-costs claim "nothing that previously worked stops working" — as written it's
   false, and it's the kind of sentence a later reader trusts without re-testing.
4. Put the observed checkout value into both refusal messages, and cover the `git-guard.sh:164`
   message too.
5. Pin message text in the tests, not just exit codes.
